# 项目中心开发模块更新 PRD

> 状态：2026-10-31 已正式发布，正式接口及桌面、手机页面核验通过；模型核对实测超时，未启用生产排程
> 范围：原项目中心“开发模块”页面内部
> 依据：`AGENTS.md`、项目地图、项目合同、模块合同和当前项目中心内容

## 1. 这页是干什么的

这是一张给钧钧自己看的开发模块图。

它只解决一件事：让钧钧一眼看清项目现在有多少个模块、每个模块负责什么、哪里缺内容，以及以后要改哪一块。

它用于开发定位；使用说明、聊天和工程实现各沿已有入口维护。

## 2. 页面结构

保留原项目中心的“开发模块”页面，不新增外部页面，不改页面入口和其他前端区域。

原来 8 个一级模块不再保留为页面结构。原页面内部按品种分页，用页签切换，每次只显示选中页的模块：

```text
开发模块
├── 英雄联盟
│   └── 该品种的开发模块
├── 足球
│   └── 该品种的开发模块
├── CS2
│   └── 该品种的开发模块
├── 无畏契约
│   └── 该品种的开发模块
└── 项目共用（同一入口内的独立分页）
    └── 真正跨品种的开发模块
```

模块总数不预设，但每个品种页只保留少量主模块；重复的合并，缺失的补上，真正跨品种的内容放到“项目共用”。

本次按现有能力收为 9 个主模块：LOL 的比赛与赛程、队伍与版本、判断与交易、记录与复盘；足球的赛事与赛前；CS2、无畏契约各自的赛事与资料基础；项目共用的资料与数据底座、项目中心与对话。后续按实际能力演变，不把数量固定为九个。

### 2.1 金字塔层级

页面按三层展开：

1. **品种页**：先看这是 LOL、足球、CS2 还是无畏契约。
2. **主模块**：每个品种只保留少量主干模块，原则上不超过 5 个；每个主模块都能直接作为后续修改对象。
3. **模块细项**：具体能力、资料来源和缺口收在主模块里面，默认折叠，不单独平铺成十几个或几十个模块。

如果主模块超过这个规模，先合并同责内容或把细项收回上一级；只有确实无法合并、且修改边界明显不同的内容才单独保留。

### 2.2 展示层与旧能力引用

- 正式展示结构使用 `development_map`：`groups[] → modules[] → detail_node_ids[]`；主模块另有 `legacy_node_ids[]` 负责旧书内跳转迁移。
- `groups` 是 LOL、足球、CS2、无畏契约和项目共用五个内部页；品种状态读取项目合同，不因出现页面就暗示能力已经完整。
- `modules` 是给钧钧直接说出的主模块；每个主模块必须有稳定的 `id`、名称、简短目的、`now`、`gaps`、`next_step` 和内部能力对应关系。待修改用新主模块 ID 保存，快照包含“品种 → 模块”，不会把不同品种合成一条。
- `detail_node_ids` 只引用现有 `module_tree` 节点或其子节点，用于折叠展开具体能力；旧能力内容仍是事实来源，不作为页面的一级结构。
- 细项补充独立的 `known_gap`，`next_step` 写待改进方向；不再把使用口令或“没有资料时返回空态”等规则拼成开发缺口。
- `module_tree`、`manual.module_tree_id` 和开发书跳转作为内部兼容引用保留；跳转会切到正确品种页并展开目标模块与细项。页面、菜单和新入口不再直接平铺旧 8 个顶层节点。

## 3. 页面上每个模块写什么

每个模块只显示三项：

- **现在有**：目前已经存在的能力或内容。
- **还缺**：明确知道但还没有、还不完整或还没验收的部分。
- **下一步改什么**：后续最直接的修改方向。

模块名称和这三项内容要足够清楚，让钧钧可以直接说“改足球里的赛程模块”或“补 LOL 里的版本模块”。

页面不展示后台路径、字段、任务命令、模型配置、代码映射和维护步骤。

## 4. 内容整理规则

- 以最新 `AGENTS.md`、项目合同、模块合同和项目地图为依据。
- 旧 8 个模块只作为待整理的旧内容，不作为新页面结构保留。
- 同一件事、同一来源、总是一起修改的内容合并。
- 责任、来源或修改方式不同的内容分开。
- 不凭空补充尚未确认的能力、来源或专业方法。
- 页面最终要能直接数清少量主模块，不让细项和重复说明制造一堆假模块。
- 每个主模块的标题下先显示一句目的，再显示“现在有、还缺、下一步改什么”；细项默认折叠。

## 5. 后台维护机制

后台维护说明不放在页面上，单独维护在 `docs/architecture/PROJECT-CENTER-MODULE-MAINTENANCE.md`，用于保证这张模块图不会再次失真。它需要记录：

- 每个品种页和模块的对应关系。
- 模块当前依据的项目事实和文档来源。
- 模块新增、合并、拆分和下线的判断规则。
- 每次内容更新的变更记录和回退依据。

后续改动项目能力、入口或缺口时，同一轮同步更新对应模块内容、菜单和跳转；开发定位入口在项目地图链接到维护说明，避免后续只看代码却遗漏这张图。

本次新增 `scripts/tasks/xiaoxue_project_center_module_review.py` 作为只读核对入口：确定性检查先核对映射，再由现有模型结合最新项目文档、项目合同和状态证据输出带来源和时间的提案；输入文档中的指令一律当作资料忽略。不确定或冲突时标记待核对，不自行编造，也不直接写回页面。维护者在已授权开发范围内核对写回；改变用户确定的分类或范围时，再由用户取舍。正式写回后读回验证，并保留变更记录和可回退版本。

本次只增加可被调用的任务入口，不注册或启用生产定时调度；后续若需自动定期触发，作为单独的调度变更按项目授权规则处理。

## 6. 原页面内要同步调整的地方

以下都属于原项目中心“开发模块”页面的同一条改动链：

- **内容正源**：在 `config/project-center-content.json` 增加 `development_map`，更新开发书链接和使用说明跳转，让它们指向新的“品种页 → 主模块 → 细项”结构；旧 `module_tree` 仅作细项事实来源和兼容引用。
- **项目中心页面**：调整 `src/modules/project-center/view.js` 的标题、层级标签、展开方式和模块分组；保留原页面入口与路由，只改页面内部展示。
- **项目中心接口适配**：让 `/api/project-center/modules` 返回 `development_map`；保留旧 `tree` 字段供兼容读者使用，但页面和菜单只读取新映射。接口入口不另建。
- **同源菜单与说明**：核对 `scripts/xiaoxue_menu.py`、项目中心使用说明和书内跳转，避免继续输出旧 8 个模块。
- **相关测试**：同步更新内容覆盖、项目中心 API、菜单来源和前端项目中心测试中对旧节点数量、名称和层级的固定断言。
- **后台维护规则**：补齐独立维护说明和只产出核对提案的模型任务入口；本次不注册生产调度，不让模型直接覆盖正源。

以下只作为事实来源或实现定位，不因这次页面整理直接改动：

- `config/project-contract.json` 和 `config/module-contract.json`：除非能力事实本身发生变化，否则只读取，不为页面分类改写。
- 普通业务页面、业务 API、数据库、交易方法、生产任务和其他前端模块：不属于本次页面内部调整。
- `memory-bank/progress.md`：完成真实改动和验证后记录证据，不作为页面模块正源。
- 旧 `module_tree` 节点 ID：本次不删除；旧顶层节点由 `legacy_node_ids` 接管书内跳转，具体能力由 `detail_node_ids` 接管折叠展示，待所有兼容引用迁移完成后再评估退役。

## 7. 本次不做

- 不新建项目中心外部页面。
- 不改普通业务页面、业务 API、数据库、交易方法或真实业务数据。
- 不把页面写成长篇使用说明或技术文档。
- 不继续保留旧 8 个一级模块作为可见结构。
- 不把后台维护规则展示给钧钧。
- 不让模型核对任务直接写回模块图或改变生产调度。

## 8. 完成标准

- 原“开发模块”页面仍能进入，但内部结构已按品种和共用内容重新展示。
- 旧 8 个一级模块不再作为可见页面结构。
- 品种页可独立切换，每次只显示一页；页签标明各自主模块数量，页内细项可折叠查看。
- 每个模块都只有“现在有、还缺、下一步改什么”。
- 钧钧可以直接按“品种 → 模块”提出修改，不需要再解释模块含义。
- 后台有独立的核对入口、变更记录和回退机制，但页面不展示这些技术内容；模型提案只读，本次不启用生产定时任务。
- `development_map`、细项覆盖、旧 ID 引用和品种归属有检查；旧书内跳转不会因页面重组失效；不同品种的待修改与备注各自保存。
