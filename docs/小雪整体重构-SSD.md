## 3A. 必须交付：关注窗口逐场准备

这部分是本 SSD 的核心施工目标，不能降为“以后按需补查”。

**输入与范围**

- 从现有当前赛事配置、已确认赛程和 preparation.upcoming_days 取得比赛集合；窗口长度不在代码或文档中另写固定天数。测试样本可用 2026-10-24 的 8 场，但正式范围随当前配置及实际赛程变化。
- 每场使用稳定比赛身份。赛程修正只更新匹配对象；待定队伍、时间和赛事信息保持待定，不猜测、不串场。
- 赛事共用材料只收集／整理一次，按赛事、队伍、版本或单场的实际适用范围复用；过期或依赖已变化时仅刷新受影响内容。

**每场准备内容**

- 赛程、赛制与本届赛事规则；当前版本及其适用性，未核实就明确标注。
- 双方相关近况、人员或阵容变化、公开观点中的主要支持和反例。只呈现来源实际覆盖内容，不把全赛季统计包装成当前状态。
- 盘口／报价只在现有资料确有且带取得时点时呈现；不得猜价，不把旧报价当临场值。
- 当前判断相关的事实、来源原文或可读正文、条件、反证与待核问题。区分事实、他人观点、项目推导和用户判断。

**补齐和有限恢复**

- 系统逐场识别缺少、陈旧、来源正文未取得、日期未知、冲突及待核内容；优先补影响当场准备的缺项。
- 复用现有来源提示、搜取预算、任务阶段、checkpoint、attempt 上限和原恢复调度。当前实现存在每任务720秒上限、单次最多6次搜索线索和8篇正文读取、最多3次有限尝试；施工应在现有配置与真实契约内核对，不得借此假称“全网查全”。
- 保留成功阶段和已取得来源；只恢复失败或输入实质变化的阶段。达到预算或尝试上限时仍交付部分成果，并写清未完成范围和具体原因，不要求钧钧逐场发送“继续”来推进既有队列。
- 不新增平行采集服务、来源目录、MCP Server、排程器或长期数据库。既有自动准备机制若未覆盖全窗口，先找出原链断点，并按权限边界实现；生产任务激活仍需单独授权。

**交付形态**

- 每个已确认比赛在原网页当前赛事入口可打开本场结果；现有产品 MCP 可读取同一比赛身份与修订，不另建第二套交互。
- 每场结果要有正文，不是只有标题、来源链接、任务状态或空卡片。若信息有限，给已确认的实质材料及缺口；赛事共用结果可复用但须说明适用范围。
- 窗口总览显示应准备场次、已有实质结果场次、部分完成场次和未能开始场次及原因，使“8场赛程”不会被误读为“8场已准备”。
- 对网页与 MCP 的合同复用现有接口，若缺批次汇总能力，在既有 current-event/API 与唯一 xiaoxue-product MCP 的输出中补齐；不得因接口未命名而新建平行入口。

**单场样本的定位**

第3节保留的 GEN–IG 仅作为具体资料卡读回、证据投影和内容质量样本，不是整批准备的代替品，也不要求重复同一研究探针。先用确定性测试验证批次覆盖、对象身份、复用、缺口和恢复；仅在修复完成后按原授权集中做一次必要的真实主路径验收。

**实施顺序与验收**

1. 以当前配置和正式赛程生成窗口清单，逐场对照原身份、已有资料和准备任务，先证明每场都进入同一批次，不静默漏项或串场。
2. 沿现有准备链复用赛事／队伍共用材料，并为每场判断哪些本场信息可直接复用、哪些已过时、哪些仍缺；只补有影响的缺口。
3. 在原任务和恢复机制内保存逐阶段结果；只续接失败或依赖变化的阶段，预算耗尽后保留已取得正文和具体失败原因。
4. 从现有网页与唯一产品工具呈现批次覆盖、逐场状态和正文。用户看到的是准备结果，不需要理解任务、尝试次数、数据库或内部队列。
5. 先以隔离的8场样本验证覆盖8/8、赛事共用材料复用、赛程变更身份更新、部分结果可读、失败阶段有限续接、上限后保留结果、网页和MCP读取同一修订。不得从测试样本写入真实资料。
6. 已知缺陷修完后集中做一次必要的实际主路径验收，并沿原入口读回。生产排程、常驻自动运行和正式外发未获授权时不启用；这不阻止完成隔离实现和接口验收。

**面向用户的状态**

- 已整理：存在可读正文及重要事实出处；没有会使本场结果失真的未解决关键缺口。
- 部分整理：有可用正文，同时明确展示时效、来源、人员、版本或其他重要缺口及原因。
- 暂无可用正文：本场仍在批次内，说明未开始或失败的具体原因和现有恢复条件。

覆盖验收以窗口内每场已确认比赛都有上述一种状态为准，不以准备任务数量或来源条数代替。未确认对阵不虚构比赛，但仍计入赛程待定说明。

## 3. C1：核对一场能直接使用的底稿

**输入与结果：** 先读原desk、已有准备和必要来源，复用双方／赛事资料，按问题补缺。应能看到正确身份、双方相关情况、影响本场的变化、对照／疑点、依据和限制。不全网重搜，不把8场全部深度研究当作前置，不新建报告格式。

**现有接点：** current_event的service.py、collection_repository.py、analysis_repository.py、evidence.py；唯一MCP的xiaoxue_prepare_match、xiaoxue_get_match_materials。

**执行分支：**

1. 有材料没接本场，或出处／条件在投影丢失、旧背景错标：沿保存输入复现，在首个错误点修，复用原字段和测试。
2. 来源缺内容：沿现有补查能力取得必要材料；不可得则交付部分底稿并说明影响，不无限追查来源。
3. 输入完整、模型仍过度推断：保留失败，交代可确认事实和待核解释；不改SOUL／模型／专业方法，不新增审查系统，不把分析标为可靠已证实结论。
4. 重要新信息未取得：显示资料截止和待补部分，不只写准备完成，也不伪装实时。

**完成条件：** 有实质内容可开始本场讨论，重要事实可回指、缺口可理解。不要求task全部completed或给下注方向；只有空态、泛泛摘要、实质错误或无依据结论不算完成。

## 4. C2：核对实际阅读与工具消费，修阻断问题

**网页：** 正式8880入口 → 当前赛事 → 该场，能读底稿、展开正文／出处、返回；同对象讨论不无故重置，不串场。未保存预案只承诺已验证的同卡重复点击保护，不承诺刷新／任意换场后永久保存。

**工具／飞书：** 原配置唯一xiaoxue-product能按比赛身份读取本场资料；当用户要求准备一批比赛时，已有飞书入口须能呈现批次覆盖和各场状态，不能把“单场读取工具存在”当作批次准备交付。网页与飞书共享同一内容修订。此要求不意味着跨端聊天记录同步。

有自然飞书记录就按该次核对，没有就标自然入站未验；不得代用户发消息、伪造入站或反复用长程CLI假充。该未验项不单独阻塞已验证网页／产品工具范围的收尾。

**完成条件：** 实际已验证入口可消费批次结果与单场正文；覆盖数与当前确认赛程一致；部分状态与缺口诚实；网页与现有产品工具不串场。复用输入未变的前批证据，只有受影响入口重验。

### 13.2 事实区块契约

- 区块 `id=facts`，排在卡片首位，由确定性代码生成，不经过模型。
- 必含：北京时间＋阶段＋BO；双方本届赛事战绩；双方本届最近三场赛果；本届交手（有则列）；官方登记名单（必须标注"含替补/青训，不代表本场首发"）。
- 每条带 `verification=official_api` 和可点回官方赛程的来源链接。
- 边界：TBD 对阵不生成；赛事未发布不生成；接口失败写"暂不可读"；不把登记名单升级为首发。

### 13.3 分析阶段契约

- 时间保留：摘要在剩余时间不足 240 秒时停止新增批次，把时间留给分析；分析单次上限 100 秒，正常约 35 秒。
- 失败不落档：分析无结果时不写 checkpoint，下一次有限恢复重跑；已成功的阶段继续复用，不重复付费。
- 资料足够就给本场判断；当前队伍事实不足时只输出条件推导，写明确认条件与失效条件，不贴强弱标签、不给比分。
- 方法级拆分（周期、版本、交易各调用一次）列为下一阶段：单次调用同时执行三份方法文档，偶发超时。

### 13.4 并发与排队

- 分池：单场比赛 2 个席位，赛事/队伍共用资料 1 个席位。共用资料不再占用单场席位，避免比赛在开赛前排队。
- 同池内按开赛时间紧迫度排序，两小时内开赛优先，其次恢复任务，最后新建。
- 每任务墙上上限 720 秒；超时保留断点，不丢已取得正文。

### 13.5 完成语义

| 状态 | 判定 |
|---|---|
| 已整理 | 事实区块完整 ＋ 本场新变化至少 1 条 ＋ 分析有结果或已声明缺口 |
| 部分整理 | 事实区块完整，但外部检索未完成或部分正文未取得 |
| 无可用正文 | 事实区块也缺，必须写明具体原因 |
