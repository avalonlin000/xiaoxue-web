## 四、核心正源和业务边界

### 1. 交易与盘口

- 交易 TK 的正式写入入口是 `/api/trading-tk`。
- `/api/market-notes` 是只读兼容投影，不恢复旧表主写入链。
- 旧 `/api/trades` 只作为只读兼容，不作为新功能写入口。
- 普通 TK、交易 TK、当前判断和赛果不能自动互相升级。

### 2. 队伍资料

- 队伍画像、TS、首发和基础队伍事实各有职责。
- 队伍画像不是 TS 数字的另一种写法。
- 旧三维只作为兼容投影，不能恢复成第二份正式画像。
- 修改画像后必须从正式读取入口读回。

### 3. 当前赛事与阵容

- 当前赛事负责当前比赛、单场上下文、资料准备和临时记录。
- 临时观察不能自动写成长期知识、画像或交易结论。
- BP 后纯十英雄阵容分析与交易判断分开；不能把队伍、盘口或赛果偷偷注入纯阵容分析。

### 4. 数据不足与冲突

- 没有数据时返回明确空态、资料不足或“暂不推荐”。
- 不能用旧比赛、相邻队伍、旧赔率或猜测填空。
- 来源冲突要保留来源、时间、冲突点和影响，不能静默折中。

## 五、每次维护的标准流程

### 改之前

1. 读取 `AGENTS.md` 和项目地图。
2. 执行 `git status --short`，确认已有未提交改动。
3. 确定唯一正源和全部消费者。
4. 判断任务属于前端、后端、数据、配置、文档还是跨层改造。
5. 先复现问题；没有复现证据时，明确标记为待核验。
6. 判断是否需要用户确认：删除、数据库迁移、真实业务数据写入、生产配置、cron、模型、Provider、密钥、权限和外部发布默认需要确认。

### 改的时候

- 只做用户目标所需的最小范围修改。
- 保护当前工作树已有改动，不覆盖、不重置、不擅自清理。
- 优先修改正源，不在镜像、缓存或兼容层里另造一份事实。
- 跨模块改动先建立影响矩阵，不能只改 grep 命中的第一处。
- 不用“新增统一层”掩盖没有解决所有权问题。

### 改之后

按影响范围执行验证：

```bash
python3 -m py_compile main.py
python3 scripts/verify_module_contract.py
node --test tests/*.test.mjs
python3 -m pytest -q
```

如果全量测试受环境依赖影响，必须区分“代码失败”和“环境缺依赖”，不能把跳过或排除测试写成全量通过。

前端构建使用独立输出目录，不直接覆盖正式服务正在使用的 `dist/`：

```bash
node node_modules/vite/bin/vite.js build --outDir /tmp/xiaoxue-web-build-check --emptyOutDir
```

必要时从真实入口验证：

- `GET /api/health`
- `GET /api/modules`
- 受影响的业务 API
- 稳定页面和对应用户路径
- 受影响的 MCP 命名工具

## 六、结构性改造规则

像“20 个模块归并为 8 个能力域”这类任务，不能直接删目录。必须先为每个目标模块建立迁移表：

| 旧模块 | 新归属 | 数据正源 | API | MCP 工具 | 前端消费者 | 测试 | 兼容策略 | 回退方式 |
|---|---|---|---|---|---|---|---|---|

实施顺序：

1. 冻结当前基线。
2. 查消费者和深链。
3. 先做内部归属或兼容适配。
4. 跑定向测试和真实入口读回。
5. 再退出旧入口。
6. 最后才删除确认无消费者的旧代码。

“模块数变少”“路由数变少”“工具数变少”都不能单独证明改造成功。

## 七、禁止事项

未经用户明确授权，不要：

- 删除真实业务数据。
- 修改或迁移业务数据库。
- 删除生产兼容接口。
- 修改模型、Provider、密钥、权限或网络配置。
- 修改生产 cron、常驻服务或发布外部消息。
- 把 `planned`、`partial` 或仅有接口响应的能力说成稳定可用。
- 把页面构建通过说成线上已经发布。
- 把 API 能读到数据说成业务入口已经完成刷新。
- 把临时记录自动写入长期画像、TK 或交易结论。

## 八、交付汇报格式

每次完成工作时，按以下结构汇报：

1. **结论**：完成、部分完成、未完成或阻塞。
2. **实际修改**：列出文件和关键改动。
3. **验证证据**：列出实际执行的测试、构建、API、页面或 MCP 结果。
4. **未验证部分**：明确环境限制、未走通的真实入口或缺少的资料。
5. **风险与回退**：说明是否影响兼容、数据、生产服务，以及如何回退。
6. **下一步**：只列仍然必要的 1—3 项，不把建议写成已完成。

结论必须区分：

- 已观察：代码、配置、命令或真实入口直接证明。
- 已推导：由多个事实推出来的判断。
- 未知：当前没有证据，不能假设。

## 九、第一次接手本项目时的任务

第一次不要直接开始模块归并。先只读检查并报告：

1. 当前工作树状态。
2. 当前 20 个后端实现模块与 8 个项目级能力模块的对应关系。
3. PRD 中的目标与当前代码的差异。
4. 删除候选的消费者和兼容风险。
5. 需要用户决定的事项。
6. 如果实施，最小安全切片是什么。

完成这份基线报告后，等待用户明确授权，再进入代码施工。
