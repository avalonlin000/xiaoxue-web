# 小雪交易方法与使用方式重组｜执行清单

## 已确认目标

小雪的主入口是聊天；Web 第二页只用于查看、打开单场、记录原始信息、回看和确认沉淀。用户不需要记方法名、页面名或流程。

用户自然说：
- “聊明天 A 打 B” → 单场赛前
- “BP 出来了”/“现在这个局面怎么样” → 同一场赛中
- “复盘刚才这场” → 同一场赛后
- “聊第三赛段/现在是什么周期” → 当前赛段框架
- “记住这个规律” → 交易 TK 候选与确认
- “聊我的交易方法” → 方法说明

## 收口后的结构

1. 证据材料：TS、队伍画像/首发、版本、BP/阵容、交易 TK、盘口、赛果；按需读取，不作为用户入口。
2. 方法库：交易总纲、周期与实力判断、版本队伍赢输法、BP/阵容、赛后校准。前台只展示人话用途、何时聊、边界；不展示 Skill、路径、工具和字段。
3. 当前赛段框架：原“大周期交易预案”改为此名称；作为阶段背景，不强制每场加载；默认展示摘要、适用范围、更新/失效条件和更新时间，可展开全文。
4. 单场线程：每场一条，分赛前/赛中/赛后。
   - 赛前：判断基础、主要矛盾、采用规律、条件分支、市场对照、原计划/不碰条件。
   - 赛中：BP/首发/比赛/市场变化，原判断维持/加强/削弱/推翻/观察，实际执行。
   - 赛后：实际发生、判断对错、执行对错、下次校准、可复用候选。
5. 沉淀候选：原“阶段整理”改名；只保留可复用赛后结论，明确归属队伍、选手、版本、交易方法/TK；单场偶然不进入。
6. 盘口记录：只保存钧钧原始判断和交易事实；赛后分析留在单场线程，长期规律进入沉淀候选。

## 强制兼容

- 不删除或迁移真实业务数据。
- 旧 `match_run_entries.section` ID 与内容必须保留。
- 每个旧 section 新增阶段元数据，恰好归入赛前/赛中/赛后之一；保留平坦 modules 数组兼容。
- 不恢复固定工作流，不自动交易，不把赛段框架自动塞给每一场。
- 不修改原始交易理念档案。

## 执行纪律与并行分工

- 一个施工任务以完整小能力为边界，预计 3–5 分钟；不把后端、前端、Skill、文档和全量测试塞进同一任务，也不拆成无意义的单文件补丁。
- 小白与 Codex 同时开工，但不得改同一文件或同一职责边界。
- Codex 负责适合独立施工的确定性代码切片：当前已改的单场三阶段后端/前端收口、对应局部测试和 build。
- 小白负责方法归类、聊天路由、共享 Skill、正式产品说明、跨层合同核对、真实入口验收与最终合并；小白不等待 Codex 才开始自己的文件。
- 每个切片结束必须先检查 diff、跑最贴近测试并报告真实完成范围；未验收的部分不得算完成。

## 实施项

### 后端
- 用单一 section 元数据定义原有条目的 label、stage、purpose。
- 当前赛事 API 新增 `stage_framework`，兼容保留 `plan_*`。
- 新增 `/api/trading-methods`，配置化返回五张精简人话方法卡。
- 模块合同增加交易方法模块，前端目录同步。
- 测试阶段覆盖、兼容 modules、赛段摘要、方法卡无内部泄漏。

### 前端第二页
- “大周期交易预案”替换为“当前赛段框架”，默认摘要、可展开全文。
- 单场展示赛前｜赛中｜赛后三段；阶段内使用小按钮/标签，不用 12 项长下拉；依据默认折叠。
- 增加最多四行“怎么用”：聊天负责分析，页面负责查看/记录/回看/确认。
- “阶段整理”所有用户文本改为“沉淀候选”。
- 增加轻量“方法与原则”展示，读取方法 API；不复制业务判断。
- 黑色工作台保持一致，移动端触控和层级清晰；不用全屏遮罩、玻璃拟态、无意义卡片和内部技术词。

### 小雪路由与正式说明
- 根 Skill 增加精炼交易使用路由：方法/赛段/赛前/赛中/赛后/记规律。
- `junjun-trading-system` 补充单场三阶段自然进入，保持不是强制状态机。
- 更新 `docs/小雪项目总使用说明.md`、`docs/交易信息系统-总体设计.md`、模块合同。
