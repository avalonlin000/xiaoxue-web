# 足球观察台 — 工程规格

> 2026-10-22｜隶属[交易信息系统工程实现](交易信息系统-工程实现.md)

## 2. 数据与结果

模块持久保存比赛身份、资料版本和各玩法结果。沿现有模块持久化惯例实现；正式存储路径在编码前核对，不能以浏览器缓存或进程内变量作为唯一副本，也不为足球直接迁移LOL业务表。

| 对象（拟定） | 必要内容 |
|---|---|
| 比赛 | 内部稳定ID、来源ID映射、联赛/赛季/双方身份、计划开球时间、来源状态和状态更新时间 |
| 资料项 | 类型、值、来源链接/ID、来源发表或生效时间、抓取时间、适用比赛、缺失原因 |
| 赛前版本 | 比赛ID、内容版本、准备时间、有效截止、资料引用、规则版本、版本身份 |
| 玩法结果 | 比赛ID、玩法、资料版本、规则版本、结果可用状态、可空的保留/排除、已检查层、首个排除层、理由引用 |
| 交易关联 | 原TK ID、football、比赛ID、玩法；原TK仍是正文唯一正源 |

`decision` 只能是 `keep`、`exclude` 或尚不能判定时的空值；空值不属于第三种判断。`readiness` 表示准备中、资料不足、结果可读或更新失败等资料状态，不能用它隐含保留/排除。

排除条件已被可靠事实证明时，其他无关缺项不妨碍排除。保留要求该玩法所有已启用的必要条件已完成，不能把“没有命中排除”直接当成资料齐全。

初盘记录必须能辨明市场、公司、总进球线及初始报价身份；当前赛前报价、收盘价、固定2.5球大/小赔率与真实初盘分别存储。仅有“最早抓到”不等于来源的“初盘”。

## 3. 当前方法如何落地

用户已将任务明确为赛前筛选，滚球盘口自己看。原始方法是讨论材料，未完成回测；不得把展示历史事实当成已验证的交易模型。

| 原方法项 | 处理位置 | 执行要求 |
|---|---|---|
| 初盘≥2.5，或指定球队进入半破圈池 | 半破赛前条件 | 只读真实初盘；球队以核实身份匹配。缺初盘且无已核实名单命中时为待补 |
| 半破初盘高位排除 | 半破规则边界 | 当前默认 `3` 或以上排除；指定球队不能绕过。25分钟对应盘口只作用户临场复核 |
| 最近一次交手半场、双方近期主/客场半场比分 | 详情事实 | 自动列真实样本、时间和比分；不虚构用户已跳过的“五项至少四项” |
| 首发阵型 | 详情事实 | 仅核实首发才这样标记；原攻击/防守阵型分组未作为完整可执行分类，缺失不直接排除 |
| 第25分钟全场盘口 | 用户赛中查看 | 不请求实时盘口，不影响赛前准备是否完成 |
| 半场角球、射门 | 用户赛中查看 | 不将赛中统计混进赛前条件 |
| 75分钟比分/盘口/小球水位、80分钟赔率 | 用户赛中查看 | 不作为赛前列表的依赖；75分钟仅是玩法名称，不是到该分钟才显示比赛 |
| 75分钟后赛前观察依据 | 独立玩法规则 | 当前按初盘≥2.5/名单圈池、最近5场晚段进失球、阵容事实执行；至少一条晚段支撑才保留，明显防守阵型且无攻击替补时排除；缺资料待补，不复制半破条件 |

两种玩法分别配置、分别求结果，共享资料。名单包括亚特兰大、哈马比、帕德博恩、广州富力、阿尔萨德、阿德莱德等用户提供名称；逐一核对来源队伍身份，历史联赛称呼不作为当前事实，不自动映射解散队到新队。

规则配置只包含已定义的类型、比较条件及证据需求，支持调整值、停用项和变更版本；不开发面向大众的规则编辑器。当前默认规则见PRD第4节，后续讨论只需调整具体阈值或事实项并增加规则版本；不得让代码偷偷改变历史版本。

## 4. 提前准备与版本保留

一次准备顺序：取覆盖范围内赛程 → 解析稳定身份 → 复用有效历史资料 → 补必要字段 → 两种玩法分别筛选 → 原子保存版本。一次来源错误不清空成功版本；失败原因与最近成功时间分别保存。

准备范围包含未来24小时及仍未结束的已知比赛；页面访问只读取结果。后台准备接入已有排程机制的独立足球职责，按来源限额去重和限频，不复制一套队列/Server。频率、首次导入及生产排程启用在来源确定后配置；本规格不启用生产任务。

开赛前资料可以产生新版本；可靠开赛状态到达后，保留已有赛前版本，不再覆写。来源未报开赛但计划时间已过时，暂停把新抓内容归为赛前，等待核实；来源明确证明延期未开赛后才可继续。既有版本若后来证明已晚于真实开赛，应标记时间不可信，不能继续冒充有效赛前版本。

资料是否属于赛前由原始时点和比赛实际状态证明。抓取时间、发布时间、事实发生时间分别保留；只有抓取时间或时间未知不能证明赛前。历史统计须限定样本截止，不能让含本场赛果的最新汇总回填旧快照。

第一次发现时比赛已开赛且没有原版本：保存赛程、展示能取得的内容为「开赛后补充资料」；不能借用事后统计生成“原先保留”。已存在赛前版本时，补充内容也不改原筛选结果。

开赛后规则版本变化不重算原结论；需要查看新规则时生成明确的新分析版本。默认归档窗口7天仅影响查询，未制定数据删除任务。

## 5. 身份、状态与时间

优先绑定供应商稳定比赛ID；内部ID不以队名+开球时间生成。跨供应商匹配同时核对赛事/赛季、双方身份与时间，不能只靠队名相似自动合并。

改期更新日程并保留旧时间和来源映射；真正取消或新建重赛的场次分别保留身份及关联，不强并。比分、状态缺失时是未知；开球时间已过不等于进行中，已过90分钟不等于结束。只有来源可靠状态触发结束归档。

存储带时区的统一时间，用户日期分组和显示固定按 `Asia/Shanghai`；显示月日和时间，跨年时带年份。默认查询合并“未结束已知比赛”与“未来24小时”，去重后排序；状态未知的过时场次显示待更新并可检索，不能永久伪装为进行中。

## 6. 接口与页面

| 接口 | 返回或职责 |
|---|---|
| `GET /api/football/matches` | **已实现只读首版**：玩法/搜索/候选或全部过滤；返回覆盖范围、更新时间、来源错误和待补结果 |
| `GET /api/football/matches/{id}` | **已实现只读首版**：按ESPN稳定ID读取比赛摘要和事件；盘口、历史样本缺失会明确保留待补 |
| 模块内部准备入口 | **待实现**：接入原排程；准备与刷新分离，幂等、可恢复，不因用户刷新重复跑 |
| `POST /api/trading-tk` | **待实现**：扩展已校验的足球/比赛/玩法关联，仍走原正式写入服务 |

浏览器刷新重读已有成果；后台刷新请求合并，不让多个页面并发触发相同抓取。较晚返回的旧响应不能覆盖已切换比赛；新列表版本暂存，保留当前阅读位置后再应用。

列表只显示已启用玩法已确认的候选；其他场次在全部比赛可查。未完成覆盖时不显示“全部筛完”；错误、空赛程、无候选和资料待补使用不同文案。

TK新增足球分类必须贯穿输入校验、正式存储、原TK列表/搜索、兼容投影和比赛详情读回；不能只把football塞进显示文案。保存关联应与TK正文同一原子操作，重复提交使用原链幂等机制或确定性提交标识，空正文和无效比赛ID不写入。比赛预填和未保存正文的本地恢复应与别场隔离。

## 7. 来源核验与接入决策

来源研究只做官方资料读取和公共GET取样。赛程/历史比分、事件时间、首发和真实初盘逐字段验证；某供应商“有赔率API”不能推导它提供本需求的历史初盘。

### 7.1 只读核验结果（2026-10-22）

- ESPN公开接口取样成功：`https://site.api.espn.com/apis/site/v2/sports/soccer/eng.1/scoreboard?dates=2026-10-23` 返回稳定 `event.id`、开球时间、双方ID/主客和 `status.type`；`https://site.api.espn.com/apis/site/v2/sports/soccer/eng.1/summary?event=401879263` 返回半场比分、双方阵型和首发、进球事件分钟，样例还返回 DraftKings 的 `total.open`/`close` 与当前水位。可先做赛程、状态、历史比分、事件和阵容适配层，但公开覆盖必须逐联赛探测，不能承诺全球覆盖。
- ESPN样例的赔率结构没有证明跨联赛覆盖、历史可回溯、亚洲盘定义或开盘时点。`total.open` 存在也不能直接升格为本需求的真实历史亚洲初盘；字段必须带供应商、市场类型、时点和证据，不满足时留空。
- API-Football官方 `https://v3.football.api-sports.io/fixtures?date=2026-10-22` 直GET返回 `Missing application key`；官方文档 `https://www.api-football.com/documentation-v3` 与定价页需要进一步授权后核验。因此它只能作为需密钥的覆盖补强候选，当前不能承诺字段、配额或价格。
- football-data 官方历史入口 `https://www.football-data.co.uk/notes.txt`、`https://www.football-data.co.uk/mmz4281/2526/E0.csv` 本次环境未完成连通性取样。即使CSV有B365/Avg O2.5等列，也不自动等于每场亚洲大小球初盘和开盘时间，必须逐列验证后才能接入。

### 7.2 推荐接入顺序

1. 先用ESPN做有限联赛的赛程/状态/稳定ID/半场比分/事件/已确认首发适配，建立来源时间和缺失语义；联赛覆盖不足的场次继续显示待补，不伪造“全量”。
2. 用户明确提供可用密钥并允许核验后，再把API-Football作为覆盖补强；密钥、套餐和生产请求不写入本次文档施工。
3. football-data只作为历史CSV补充，先完成连通性、目标联赛、字段和初盘含义探测；无法证明初盘时只展示历史事实，不参与半破保留条件。

因此当前可以确定“赛程和部分历史/阵容资料能做适配”，不能确定“所有目标联赛都有资料”或“真实初盘已解决”。在初盘来源合同未验证前，半破相关比赛可展示资料但结果保持待补；不得用当前盘、收盘或固定2.5赔率替代。

## 8. 实施顺序和验收

在同一完整功能内按依赖施工，不缩成另一版MVP：先定可取得字段和规则映射，再实现持久资料与独立玩法结果、原页面、TK贯通，最后接提前准备并验收。

| 验证 | 必须证明 |
|---|---|
| 规则/缺失 | 两玩法不同结果；初盘缺失不按0；缺必要证据不假保留；人工赛中字段不参与 |
| 准备与版本 | 后台未打开页面也准备；重启可读；失败保留旧版；开赛后补充与原版分离 |
| 时间与身份 | 北京跨日不丢；开赛/结束不靠时钟猜；延期、改名、重复来源不丢原TK |
| TK副本写回 | 原入口保存→原列表/足球分类/比赛详情读回；重复点击不重复，非法输入不污染 |
| 桌面/手机 | 真渲染，无横向溢出，详情返回保留位置，慢响应不串场 |
| 真实来源路径 | 实际覆盖联赛的真实比赛，取得可靠赛前字段、来源和时点；不能只验mock列表 |

文档验证只查引用、状态与差异。进入实现后执行相称单测、Python编译、独立outDir构建和隔离页面/API验证；正式发布及生产自动准备启用沿项目规定单独核对授权，真实业务TK不用于试写。
