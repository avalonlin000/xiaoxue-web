# 小雪赛前方法引导与主要矛盾判断 PRD

> 状态：已实施（2026-10-25）。`xiaoxue-prematch-guide` 与项目中心 `prematch-materials` 入口话术已按 7.1／7.2 对齐；真实入口多轮对话验收尚未执行，完成与否仍以真实结果为准。
> 层级：项目。作为《交易信息系统-总体设计》的 LOL 赛前交互专项需求，复用项目中心“当前赛事与单场”“方法与判断”“TK 与交易记录”及 `config/module-contract.json` 现有正源；不新增平行产品、用户模块或数据正源。
> 现有相关 PRD《交易信息系统-总体设计.md》《当前赛事信息收集能力重构-PRD.md》当前标记为历史冻结。本文件只补充本次已确认的赛前使用方向，不宣称替代或改写它们。

## 1. 功能概述

用户开始准备一场 LOL 比赛时，小雪先简洁整理这场已有的可靠信息，再从用户现有、用过的方法中带出少量可能有帮助的观察角度。用户自己判断本场主要矛盾；小雪随后围绕用户选定的矛盾继续协助。

这是半自动的赛前辅助：小雪省去重复找资料、整理资料和回忆方法的精力，但不替用户选定本场重点、拼成自动结论或决定交易。

## 2. 背景与动机

小雪已有当前赛事与单场、方法与判断、TK 等能力。用户需要的不是更多模块或更长的问答流程，而是在赛前尽快看到“这场目前已知什么、我过去用过的方法哪些可能派得上用场”，然后由自己抓住这场特有的主要矛盾。

每场比赛的主要矛盾会变化，不能预先固定成通用清单，也不能因为系统能调用方法就替用户完成取舍。自用项目的价值以减少用户操作和等待为先。

## 3. 目标与指标

- 赛前开场就能复用系统已有的本场信息，不要求用户重述已保存内容。
- 方法提示少而相关，能帮助用户想起可用的既有方法，不要求用户记方法名或逐项点选。
- 用户能够用自然语言指出、修正或改变本场主要矛盾，小雪顺着该判断继续，而非反复把流程交回用户调度。
- 不让用户为了让系统工作而进行多轮盘问、填表或重复确认。

本需求不以自动判断率、方法覆盖数量、输出长度或自动产出交易 TK 数量作为成功指标。

## 4. 目标用户

| 用户 | 目标 | 使用场景 |
|---|---|---|
| 钧钧（自用者） | 快速了解本场已知信息，并借助熟悉的方法展开自己的判断 | LOL 赛前准备和继续讨论某场比赛 |

## 5. 功能范围

### 5.1 包含功能

- 从现有单场与资料正源读取并整理本场已知信息；信息标明为已知、未确认或暂缺，不把推测写成事实。
- 结合本场问题和已有上下文，检索用户已使用或认可的相关方法、方法材料及相关 TK；仅提示少量可能相关的内容，并用简短人话说明各自能帮助观察什么。
- 方法提示用于唤起思路，不是方法目录、必选项、执行清单或推荐主要矛盾。用户可以不采纳提示，也可以直接提出自己的重点。
- 用户指出本场主要矛盾后，小雪围绕这个矛盾继续协助；用户修正重点时随之切换，不要求重走准备流程。
- 资料暂缺或方法关联不确定时，简短说明限制后继续已有讨论；只有比赛对象等关键歧义会改变结果时才询问。
- 若后续用户明确要整理或写入交易 TK，沿用现有 TK 入口与写入边界处理；赛前准备本身不默认生成或写入 TK。

### 5.2 不包含功能

| 不包含 | 理由 |
|---|---|
| 替用户自动判定本场主要矛盾或最终交易结论 | 主要矛盾随比赛变化，是用户本场判断与取舍的核心 |
| 自动一条龙地跑完整套方法并输出最终交易 TK | 用户确认的是半自动协作，不是自动替代判断 |
| 新增项目中心模块、页面、字段、数据表、方法目录或平行 TK 库 | 现有项目中心与开发模块已承载相应能力；当前目标是减少交互，不扩建系统 |
| 固定每场必走的资料/方法/确认步骤或要求用户填表 | 会把辅助工具变成用户的额外工作 |
| 自动把单场观点升级、写入或修改长期 TK | 单场讨论与长期知识有不同边界；只沿用既有明确写入规则 |
| 把纯十英雄阵容分析强行并入赛前交易判断 | 保留现有方法分工，是否需要由用户问题和本场输入决定 |

### 5.3 后续迭代

当前不预设新增功能。先依据本 PRD 对现有真实入口做使用验证，再由钧钧决定是否需要调整。

## 6. 用户故事

### 6.1 P0 — 必须满足

- **US1：快速看到已知信息**：作为钧钧，我想准备一场比赛时先看到系统已经知道的关键信息，以便不用自己重复查找和复述。
  - **验收标准**：Given 指定比赛且已有相关资料，When 我开始赛前准备，Then 小雪从已有正源整理与当前问题相关的信息，并区分已确认、未确认和暂缺，不把整份资料库倾倒给我。
- **US2：被已有方法启发而不是被流程支配**：作为钧钧，我想在需要时看到少量自己用过的方法能帮助观察什么，以便自然进入分析而不必先回忆方法名。
  - **验收标准**：Given 我的方法或相关 TK 可从现有来源找到，When 小雪展示本场准备，Then 它只提示少量相关方法及用途；不展示无差别长目录，不要求逐项选择或执行。
- **US3：由我确定主要矛盾**：作为钧钧，我想自己决定这场先看什么，以便每场按实际情况判断。
  - **验收标准**：Given 小雪已呈现已知信息和方法提示，When 我指出或修正本场主要矛盾，Then 小雪围绕我的重点继续并保留上下文，不以自己的候选覆盖我的判断，也不要求重述已有信息。
- **US4：少打断地处理不完整信息**：作为钧钧，我想让讨论在一般资料缺口下仍能继续，以便不被一连串问题卡住。
  - **验收标准**：Given 有非关键资料缺口，When 小雪准备或分析，Then 它简短标明限制并继续可做部分；只有会改变比赛对象或回答实质的歧义才提出必要问题。
- **US5：单场内容不暗中变长期内容**：作为钧钧，我想保留单场讨论与长期 TK 的边界，以便我的暂时看法不会被误当成长期认可。
  - **验收标准**：Given 我进行普通赛前讨论，When 讨论形成观点，Then 系统不自动写入或改变 TK；只有我明确提出相应整理/写入意图时才使用现有正式入口。

### 6.2 P1 — 体验优化

- **US6：自然切换讨论重点**：当我临时改变主要矛盾或想采用另一种已有方法时，小雪直接沿当前对话切换，不让我重新发起赛前流程。
  - **验收标准**：Given 单场上下文仍在，When 我以自然语言改变重点，Then 后续回应基于新重点且不重复已经给出的背景。

### 6.3 P2 — 未来考虑

本版不定义 P2 功能，避免把尚未验证的想法提前变成产品范围。

## 7. 功能详细设计

### 7.1 核心交互

1. 用户说要准备某场或在当前赛事页进入该场。沿用现有赛前统一入口和单场能力，不要求另一条口令或手工启动模块。
2. 小雪读取当前单场已有材料，只整理与赛前判断相关、当前可信的信息。首轮先给简短的“已知 / 尚未确认”，不等所有资料齐全才开始，也不把目录和缺口清单整份倒给用户。
3. 小雪检查当前问题和上下文中已出现的方法、项目现有方法材料及相关 TK。只带出少量与本场有关的既有方法，说明“它可以帮你核对什么”。若来源只能证明方法存在、不能证明用户用过，不说“你以前用过”；若没有相关方法依据，就不硬凑提示。
4. 小雪把判断空间留给用户。可以自然地问一句“你觉得这场先看哪一点？”，但用户也可以直接继续、纠正或跳过；不要求回答该问题才能推进。小雪不得把自己的提示宣布为本场主要矛盾。
5. 用户指出关注点后，小雪沿该方向使用相关方法、补充必要材料并继续分析；用户中途换重点时直接切换，不复述全套背景、不重启流程。
6. 一般资料缺口只说明对当前判断的影响并继续可做部分；只有比赛身份等关键歧义会实质改变结果时才提问。用户明确要求整理或写入 TK 时，另按现有入口和边界处理。

这是对现有赛前入口的行为约定，不是需要用户逐步完成的工作流。用户可直接提问、跳过方法提示、改变方向或结束；小雪不以用户回复“继续”作为内部推进条件。

首轮表达形态（按本场内容自然组织，不要求逐字套用）：

> 这场目前确认的是……；……还没确认。X 方法可以帮你核对……。你想先看哪一点？

不把“主要矛盾”当作用户必须填写的术语。用户用自己的说法指出关注点即可。若用户尚未明确，小雪可给少量观察线索供用户取舍，但不连环追问，也不擅自替用户定主次。

### 7.2 执行落点与改动边界

当前可确认的落点是现有 `xiaoxue-prematch-guide` 赛前统一 Skill、项目中心“赛前资料与单场准备”的对话入口，以及 `current_match`、`version_lineup`、`tk` 三个既有开发模块。当前项目中心入口话术含“先列出可靠资料、主要矛盾和缺口”，现有赛前 Skill 又规定固定议程、每轮一个问题并停等用户；这两处表达与本 PRD 的“用户自己定主要矛盾、减少陪聊”不一致，应在实施时沿现有正源调整。

本需求的最小实施只做以下现有落点的行为对齐：

| 现有落点 | 实施要求 | 不做 |
|---|---|---|
| `xiaoxue-prematch-guide` | 将单场赛前引导从固定逐步议程改为“先给已知信息 + 相关方法提示 + 把重点交给用户”；用户明确重点后按需深入；用户想要完整分析时仍可一次给全 | 不新建第二个赛前 Skill，不要求每轮都问问题或等“继续” |
| 项目中心 `prematch-materials` 对话入口 | 将现有提示语改为“帮我准备这场：先整理已有信息，再提示我可能用得上的方法；这场主要看什么由我来定。” | 不新增项目中心节点、卡片或口令 |
| `current_match` / `version_lineup` / `tk` | 复用现有单场材料、方法及 TK 读取能力；按用户当前焦点选择调用 | 不增加 API、字段、表或平行写入路径 |

如果实施前核对发现以上入口或字段已变化，执行者应按当前项目中心和模块合同找到同一现有落点，不照抄过期路径；如果必须新增能力或改变数据契约才能实现本 PRD，应先报告具体用户体验影响，不自行扩范围。

### 7.3 现有模块分工

| 项目中心/开发模块 | 本需求中的职责 | 边界 |
|---|---|---|
| 当前赛事与单场 | 提供本场身份、已有材料和临时讨论上下文 | 不将本场临时状态冒充长期知识 |
| 方法与判断 | 按需检索并带出相关的既有方法，支撑用户自己的判断 | 不把“能调用方法”变成自动跑完方法或替用户选重点 |
| TK 与交易记录 | 提供相关既有认识；在用户明确要求时复用现有整理/写入能力 | 普通讨论不自动写入、认可、升级或修改 TK |

以上为现有模块间的产品行为约定，不要求增设用户入口、页面、字段或正源。工程实现需以现有 `config/module-contract.json`、各模块实际能力和当前能力底图为准；PRD 不宣称这些交互已在真实入口完成验收。

### 7.4 数据模型

不新增数据实体或字段。复用现有单场运行上下文、资料/TK 正源和方法来源；具体映射与读写仍由现有模块合同和工程文档约束。

### 7.5 AI/Agent 行为约定

- **定位**：小雪是资料整理者和方法引导者，用户是本场主要矛盾及最终判断的负责人。
- **输入**：用户指定的比赛、当前对话、本场已有资料、能够确认来源的用户既有方法/TK。
- **输出**：与当前问题相关的已知信息、必要的不确定性、少量方法提示，以及对用户所选重点的后续协助。
- **方法来源**：不得仅凭模型推测声称“你用过/认可过”某方法；没有可追溯材料时可说明为现有可选方法或不提示，不伪造用户历史。
- **主要矛盾边界**：可提供观察线索，不把系统猜测标记为用户已认定的主要矛盾；用户明确指出后优先跟随用户判断。
- **交互效率**：不要求用户学习工具名、方法名、固定口令或按步骤答题；不重复询问已在当前上下文或正源中可用的信息；一次只问会实质改变回答的关键问题。
- **事实边界**：事实、暂时推导和用户判断需能区分；资料过时、冲突或缺失时如实简述影响。
- **写入边界**：普通讨论不触发长期写入。用户明确要求整理或写入 TK 时沿用现有入口和状态规则；不新增确认门，也不绕过既有边界。
- **失败降级**：相关资料或方法暂时读不到时，说明当前依据有限并继续可回答部分；不虚构已读取、已分析或已写入。

## 8. 非功能需求

### 8.1 性能与交互效率

- 首次回应先呈现本场最相关的已知内容和方法提示，不等待用户逐项编排模块。
- 输出以便于用户快速判断为目标，避免默认长报告、重复背景和无关方法清单。
- 具体响应时限沿用现有运行要求；本 PRD 不虚构尚未测得的秒数指标。

### 8.2 安全与写入

- 遵守现有单场与 TK 的正源、对象归属和写入边界。
- 不自动下单，不把方向辅助表达成已执行交易。
- 不因本场讨论自动修改长期画像、方法、版本理解或 TK。

### 8.3 兼容性

- 保留现有自然语言对话、当前赛事工作区、方法与判断及 TK 入口；不强迫用户改变已能使用的路径。
- 不恢复已退役的盘口/交易旧入口或平行写入路径。

## 9. 成功指标

### 9.1 先行指标

使用真实赛前对话检查：用户是否能在首轮看到已有信息；是否无需复述系统已有内容；方法提示是否短且有用；用户能否自然指出主要矛盾并让讨论继续；普通讨论是否未触发 TK 写入。

### 9.2 滞后指标

以钧钧实际使用反馈为准：赛前为组织资料和回忆方法所花的交互是否减少，且主要矛盾仍由钧钧自己把握。单一使用频次或自动化程度不作为独立成功证明。

## 10. 验收标准

使用至少一场真实赛前对话，从现有用户入口验证：

1. 指定比赛后能读取并简洁呈现已有且相关的本场信息；确认事实与不确定项不混写。
2. 有可追溯的相关方法/TK 时能给出少量有用提示；没有时不伪造用户历史或强行列目录。
3. 用户可以自然地指出本场主要矛盾；后续分析围绕用户所选方向推进，且不要求重报背景。
4. 用户改变关注点时可以在当前上下文切换；不要求从头开始或逐项调用方法。
5. 一般资料缺口不阻断其余讨论；会改变比赛身份或回答的关键歧义才澄清。
6. 普通赛前对话不会暗中写入、升级或修改 TK；明确的 TK 请求仍走原正式入口，并按既有方式读回。
7. 整个路径没有新增模块、页面、字段、数据表或强制清单，也没有要求用户长时间陪系统逐步交互。

以上验收尚未执行；完成与否以真实入口结果为准，不能由本 PRD 或单元测试本身宣称。

## 12. 实施顺序与验收用例

实施只围绕一个垂直用户路径，按以下顺序推进；每步发现现有行为已满足时保留，不为“完成步骤”而改造：

1. **对齐旧入口表达**：检查项目中心单场赛前提示与现有赛前 Skill 的固定议程/逐轮提问规则，按 7.1、7.2 的行为约定改到一致。
2. **接通现有材料**：从真实入口确认单场已知信息可读取；按当前问题按需取方法或 TK，不要求所有方法都加载或执行。
3. **让用户接管重点**：用用户自然表达指出的矛盾继续对话，保留单场上下文；不要求用户逐项回复、不以“继续”作为推进开关。
4. **验证长期写入边界**：普通讨论不写 TK；只有明确 TK 请求才进入既有正式写入路径。若验收涉及真实业务写入，须按项目规则另行确认并读回。

### 12.1 真实入口验收用例

| 用例 | 操作 | 通过表现 |
|---|---|---|
| 首轮准备 | 在正式小雪入口自然提出“准备这场 [比赛]” | 首轮先给本场已有的相关信息和不确定项；没有长报告、固定议程或先盘问用户 |
| 方法提示 | 使用一场已有相关方法/TK 的对局 | 只提示少量相关方法及用途；不要求用户选方法名，不声称没有来源支持的个人使用历史 |
| 用户定矛盾 | 用户回复一个具体关注点，例如“我觉得关键是前期节奏能不能滚起来” | 小雪围绕该点继续，不把其他候选强行排在前面，不要求用户重述背景 |
| 中途换重点 | 用户随后改说想先看另一个矛盾 | 小雪沿用同场上下文切换，不重跑全流程、不要求重新提供已有资料 |
| 一般缺口 | 本场有非关键资料暂缺 | 小雪简短说明影响并继续已能讨论的内容，不连续追问 |
| 无可证方法史 | 当前上下文/TK 没有证据证明用户用过某方法 | 不说“你以前用过”；有明确相关的现有方法材料时只按其真实身份介绍，否则省略方法推荐 |
| TK 边界 | 只进行赛前观点讨论，不提出写入请求 | 不发生 TK 写入或状态修改 |

以上用例至少在正式用户入口完成一轮自然多轮对话；记录实际输入、可见回复及是否出现重复提问。仅 Skill 文件修改、项目中心配置通过或本地工具调用成功，均不单独代表用户路径通过。未实施前，本 PRD 只定义目标，不授权代码、部署、生产任务或真实业务数据写入。
