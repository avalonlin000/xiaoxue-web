# 交易人生：品种业务指导与文档整理方案

以后日常只认五份核心业务文档：一份 `AGENTS.md` 管整个项目共同遵守的规则，LOL、足球、CS2、无畏契约各一份业务指导，讲清这个品种怎样帮你、先给你看什么、怎样判断、怎样才算做好。每次不用全看，做足球就读总规则和足球指导，做 LOL 就读总规则和 LOL 指导。原来散在总规则、旧方案、页面、配置和聊天里的要求，会归到对应位置；需要技术细节时，再顺着链接看实现。业务要求改了就改对应品种指导，共同规则改了就改 AGENTS，旧方案保留在历史区，不再和现行规则一起生效。

> 状态：2026-11-02 已实施并完成专项验收，已转为历史方案；正式约定以根 `AGENTS.md` 和四份品种业务指导为准。
> 层级：项目。执行授权来自钧钧当次“执行并且提交上线”；真实赛前多轮入口和模块核对生产排程等未完成项不因本文归档而改变。
> 本文只解释本次整理如何落地，不是新增的长期总规则，也不替代现行进度与交付证据。

## 1. 从现在到整理后

| 事项 | 现在 | 整理后 |
|---|---|---|
| 项目共同规则 | AGENTS 已承载项目定位、边界和入口，也夹有足球专项要求 | AGENTS 保留共同规则，增加品种指导入口和读取、更新约定 |
| 品种业务要求 | 分散在 AGENTS、专项需求、配置、页面文案和聊天中 | 每个真实品种一份正式业务指导，作为使用目标、产品行为和验收依据 |
| 开发定位 | 已有按品种划分的开发模块图和技术地图 | 保留；用于找到改动位置，不承担第二套业务规则 |
| 实现与字段 | 项目合同、模块合同、配置、代码和数据已有各自来源 | 保留；指导引用这些来源，不另建数值表、数据库或实现 |
| 旧方案与历史 | 已有归档区和部分旧路径跳转，仍有专项需求需要判断去向 | 有效要求先吸收，活跃引用先迁移，历史证据保留在归档区 |
| 日常阅读 | 需要判断多份材料是否仍有效 | 先读 AGENTS 和当前品种指导，按任务展开技术材料或状态证据 |

“五份”只指当前四个品种加总规则的核心业务文档，不是把整个仓库压成五个文件。以后正式增加一个真实品种，就增加一份对应指导；“项目共用”是公共能力分组，不单独算交易品种。

## 2. 目录与文件职责

下列为目标结构，尚未创建的文件以本方案为拟定路径：

```text
/home/ubuntu/xiaoxue-web/
├── AGENTS.md                       项目总规则与阅读入口
├── docs/
│   ├── README.md                   简短索引，只导航，不另写规则
│   ├── business/
│   │   ├── lol.md                  LOL 业务指导
│   │   ├── football.md             足球业务指导
│   │   ├── cs2.md                  CS2 业务指导
│   │   └── valorant.md             无畏契约业务指导
│   ├── architecture/              技术地图与维护说明
│   ├── requirements/              正在讨论、实施或验收的专项需求与方案
│   └── archive/                   已被替代、已结束的方案与历史证据
├── memory-bank/                   当前进度与变更记录
├── config/                        项目、模块合同与运行配置
├── src/                           现有前端实现
├── xiaoxue_api/                    现有后端实现
└── scripts/                       现有任务与工具入口
```

业务文档按品种归类；代码继续按现有实现职责组织。本次不为了文档对称而重排源码，不移动外置业务数据库和 Wiki，不复制专业 Skill，也不更换项目、接入助手或现有服务的身份。

各类材料分工如下：

- AGENTS：共同定位、职责、安全和写入边界，何时读取指导、何时同步更新。
- 品种指导：用户目标、使用方式、默认展示、判断含义、资料限制和验收场景。
- 技术地图与合同：实现位置、接口字段、能力范围、依赖和配置来源。
- 项目中心内容：面向用户展示能力、用途、缺口和入口，业务表述与指导一致，展示结构仍沿现有合同。
- 进度和交付记录：本次做了什么、何时验证、验证范围、尚未解决的问题。
- 专项方案：解释一次具体改动如何落地，交付后的有效规则回到正式来源，方案保留作追溯。

业务指导描述“应该怎样服务用户”，不能因代码当前做不到就改写已确认目标；代码、配置和数据证明“实际怎样运行”，也不能因指导写了目标就声称实现完成。两者有差异时，在当前任务证据中明确记录要求、实际行为和差异。

## 3. 每份业务指导必须写出的内容

每份使用相同的六个主题，但内容必须来自该品种现有要求，不交付四份只换标题的模板：

1. 用户要什么：实际问题、使用目的和最终由用户作出的取舍。
2. 怎样使用：常见场景、现有入口、页面与对话各自职责；允许从实际问题直接开始。
3. 先展示什么：默认结果和阅读顺序，哪些内容首屏可见，哪些按需展开。
4. 怎样判断：现有方法的用途，事实、推导和用户判断怎样区分，结果标签各自意味着什么。
5. 资料和能力边界：缺失、过时、冲突、来源失败如何表达，哪些事项仍需用户复核。
6. 怎样验收：具体输入、用户可见结果、应保持的边界以及对应实现和方法来源。

数值阈值、名单、字段定义和专业方法继续由各自正式来源维护。指导用大白话解释用途和判定口径，必要的解释或例子标明来源；不得维护一套脱离配置、代码或正式方法的独立规则。

### 3.1 LOL 指导的业务重点

- 区分查队伍、赛前准备、纯十英雄阵容分析、交易方法讨论、记录和复盘，不强制用户按固定流水线操作。
- 赛前先整理本场已有的可靠信息，区分已确认、未确认和暂缺，只提示少量有依据的相关方法；用户决定本场主要关注什么。
- 只问画像、首发或队伍资料时，展示五项画像及明确请求的事实，不自动附加 TS、TK 或盘口。明确要求组合时再按需读取。
- 纯阵容分析与完整交易讨论保持现有分工，具体执行引用正式专业方法，不在指导里复制一套分析引擎。
- 普通讨论不自动改写长期画像、版本理解或 TK；明确要求保存时沿原正源写入并读回。
- 验收至少覆盖：已有资料无需用户重述；改变关注点后能继续；资料不足时不编造；只查画像不会扩展成交易分析；普通讨论没有暗中长期写入。

赛前部分承接现有[赛前方法引导需求](赛前方法引导与主要矛盾判断-PRD.md)。其文首状态注明已实施但真实多轮入口未验收，迁移文字时必须保留这项未完成事实，不能据此宣布已验收。

### 3.2 足球指导的业务重点

- 核心用途是赛前观察清单：进入后直接认出哪些比赛适用半破或75分钟后，以及相应的事实依据。
- 默认清单只取两种玩法“保留”结果的并集，同场只出现一次。仅待补、排除或不在圈池的比赛不进入默认清单，仍能在“核对全部”查看。
- 每场先展示中文对阵、北京时间、适用玩法和每个保留玩法的一句具体事实理由。双玩法并列，不据此自动排优先级。
- 半破要区分初盘入池依据与上半场历史支撑；75分钟后要说明圈池和晚段历史依据。关键判定资料不足时待补，辅助样本不足要说明，不能自行改写已有保留规则或编造样本。
- 展开后可核对完整理由、来源和资料缺口，清单仍可操作；临场盘口、比分等继续由用户按现有分工复核。赛前保留不等同交易决定。
- 筛选实现和数据来源继续定位到现有足球后端与配置，历史 PRD/SSD 只提供追溯，不重新成为另一套现行规则。

足球验收必须覆盖以下场景，不能只证明接口返回成功：

| 场景 | 用户应看到的结果 |
|---|---|
| 仅半破保留 | 默认清单出现一次，只把半破作为适用玩法呈现 |
| 仅75分钟后保留 | 默认清单出现一次，显示对应玩法及晚段事实理由 |
| 两种玩法都保留 | 同场一张卡，分别说明两种玩法，不自动加优先级 |
| 无任何玩法保留 | 不混进默认清单，可从“核对全部”查看结论和原因 |
| 有支撑样本 | 卡片能直接解释关注依据，详情可核对原始事实，数字与事实来源一致 |
| 辅助样本缺失 | 如实显示缺口，保留状态仍按现行规则，不生成虚构支撑 |
| 关键资料缺失或来源失败 | 分别呈现待补或读取不完整，不伪装成“没有符合比赛” |
| 展开依据和切换玩法 | 清单仍可操作，同场不重复，桌面与窄屏可正常阅读 |

前次只读核对已观察到：前端理由展示只取数组第一条，半破后端通常先放初盘入池条件，再放上半场历史支撑。这是一项需要按上述业务目标核对的呈现差异，不因写完指导就视为修复。本次未重新运行页面验收，也不据此宣布当前线上结果。

### 3.3 CS2 指导的业务重点

- 围绕用户点名的赛事、地图、队伍或市场问题，使用已有专项方法、普通 TK、交易 TK 和原文依据。
- 先回答当前问题，并交代资料适用的时间、对象和缺口；资料与未来判断分别表达。
- 现有项目合同仍记载地图、选手状态、赛程、盘口和结果覆盖不完整，不能承诺完整实时工作台。
- 验收至少覆盖：已有认识可查回依据；缺关键本场资料时能说明影响；不会把历史材料包装成当场事实或把 LOL 页面当作 CS2 已接通入口。

### 3.4 无畏契约指导的业务重点

- 用现有专项讨论与 TK 材料解释问题，查回一条认识的来源和适用条件，再判断能否用于本场。
- 区分历史材料、已核实本场事实和仍待核实的信息；价格必须说明时间与来源，不能用历史赔率冒充实时价格。
- 当前赛事、价格和跨游戏单场至复盘链的覆盖按现有合同如实说明，不因已有品种页就宣称全部接通。
- 验收至少覆盖：认识可追溯；本场适用性有依据；旧价格不冒充实时价格；没有用其他品种入口补成不存在的本品种能力。

CS2 和无畏契约本次只整理已确认范围，尚未定义的专属玩法不由写文档者推测补齐。

## 4. AGENTS 的拟调整内容

开头由“项目层唯一的现行约定”调整为“项目总规则”，并明确具体品种业务指导的职责，避免五份正式文档之间含义冲突。拟加入以下约定，实际文字以审阅后的版本为准：

> 本文件维护项目共同规则；各品种业务指导维护该品种的使用目标、展示要求、判断口径和验收标准。LOL、足球、CS2、无畏契约分别读取 `docs/business/lol.md`、`docs/business/football.md`、`docs/business/cs2.md`、`docs/business/valorant.md`。
>
> 处理品种业务解释、需求、页面、筛选、资料呈现或验收任务前，先读 AGENTS 和对应品种指导，再按任务读取技术地图、模块合同及正式方法。跨品种任务读取受影响的指导，不要求每次加载所有品种。单纯检索某条事实或执行已有技术操作，按现有入口读取所需材料，不额外制造通读负担。
>
> 用户确认的目标、使用方式、展示重点、判断口径、资料边界或验收标准变化时，同轮更新对应指导；仅内部实现变化、业务行为不变时无需改写指导。共同规则变化时更新 AGENTS，入口变化时同步现有索引。
>
> 数值、名单、字段、能力状态和专业方法继续引用原正式来源。指导与实现不一致时记录业务要求、当前行为与差异，不以当前缺口覆盖已确认目标，不把目标文字当成已完成证据。
>
> 实际验证时间、环境、结果和未完成项写入现有进度或交付记录。普通讨论、临时观点不会因出现在聊天里就自动成为正式规则；经用户明确确认的规则变更才沿上述位置更新。

现有足球专项正文并入足球指导后，AGENTS 原处保留简短入口；仅适用于 LOL 的展示要求并入 LOL 指导。共同的事实、写入和安全边界仍保留在 AGENTS，不在四份指导里全文复制。

## 5. 历史材料怎么处理

清理以减少有效规则的分叉为目标，不按文件日期一刀切，不把当前未验收任务藏进历史区。

| 对象 | 处理结果 |
|---|---|
| 根 AGENTS | 保留，按第4节调整职责和引用 |
| 四份品种指导 | 新建，承接相应已确认的业务要求 |
| `docs/README.md` | 保留为唯一简短文档索引，增加四份指导入口，不扩写另一套总说明 |
| `docs/architecture/PROJECT-MAP.md` | 保留技术导航，补充业务指导定位，避免复制指导正文 |
| `docs/architecture/PROJECT-CENTER-MODULE-MAINTENANCE.md` | 保留开发模块维护职责，业务目标引用正式指导，技术维护细节继续留在原处 |
| `docs/PROJECT-MAP.md`、`docs/小雪项目总使用说明.md`、`memory-bank/modules.md` | 当前都是兼容入口；先核对调用方并更新引用，仍被使用时只保留准确跳转，不再扩写正文 |
| `docs/archive/designs/赛前方法引导与主要矛盾判断-PRD.md` | 有效业务要求已并入 LOL 指导；真实多轮入口验收未完成的事实继续保留在进度和交付证据中 |
| `docs/archive/designs/项目中心开发模块更新-PRD.md` | 已发布要求和现行维护说明已分开承接；模型核对超时、未启用排程的边界继续保留 |
| `docs/archive/` 中旧 PRD、SSD、说明和审计 | 保留历史证据，不重新激活、不改写成当下状态，也不要求日常读取 |
| `memory-bank/progress.md`、变更记录和交付证据 | 保留动态状态和历史事实，不复制成业务规则、不为凑文档数量而删除 |
| 本方案 | 已迁移到历史区；最终规则回到 `AGENTS.md` 和对应的四份品种业务指导 |

当前不指定任何永久删除文件。后续若要删除已无调用的重复文件，应先列出精确对象、证明正式替代来源和引用已迁移，按项目既有授权边界处理。

本次迁移先保留了受影响文件与未提交改动的可恢复快照，再按“写正式内容 → 更新活跃引用 → 验证 → 归档旧正文”的顺序完成。外部 Skill 或工具如仍引用旧路径，后续应列明调用方并保持安全跳转，不借整理文档扩大为外部配置或 Skill 改造。

## 6. 以后更新只改哪里

| 变化 | 应更新的位置 | 无须连带改写的内容 |
|---|---|---|
| 足球怎样选、先展示什么、怎样解释理由 | 足球指导；涉及行为时由后续授权任务对齐实现和验收 | 其他三份品种指导 |
| LOL 某种使用场景的目标或判断边界 | LOL 指导及被影响的原方法或入口 | 与该变化无关的品种和共同规则 |
| 项目职责、共同边界、读取或同步原则 | AGENTS | 各指导无需复制总规则全文 |
| 阈值、名单、字段或配置变化 | 原配置、合同或正式方法；影响业务口径时同步指导 | 不新增第二套参数表 |
| 接口或页面内部修复，用户行为未变 | 原实现、相关测试和本次证据 | 不为显示维护动作而改指导 |
| 用户能看到的能力、入口或缺口变化 | 对应指导和原项目合同、模块合同、项目中心内容中的受影响部分 | 不重写无关合同或整张开发模块图 |
| 本次任务的验证结果、阻塞和下一步 | 现有进度或交付记录 | 不写进长期业务正文 |
| 新增真实品种 | 对应的一份指导、AGENTS 和既有索引及能力注册，并纳入现有模块核对任务的读取范围 | 不复制整套项目规则或另建 Agent |

简单调整直接修改正式来源，不强制每次新建 PRD、SSD。确需单独设计的任务可以有专项方案；任务结束后把有效规则收回对应指导，方案归档，尚未完成的验证继续留在现有任务证据中。当前不新增自动同步任务、模型巡检或生产调度。

## 7. 后续实施顺序与验收

下列是审阅后的实施建议，不是本次已执行事项：

1. 核对当时工作树与受影响文档，建立每项现行要求的来源和目标位置，同时定位读取这些文档的现有任务及合同测试，确认仍有效与仍未验收的内容。
2. 在项目层路径检查通过后，写出四份有具体业务内容和验收场景的指导；既有数值、字段、方法和数据正源保持唯一。
3. 更新 AGENTS、文档索引和必要的技术导航引用，确保从总入口能够找到每个品种。
4. 核对项目中心展示与正式指导的关系；只有业务文案需要对齐时才在已授权范围内调整原展示内容，不把文档整理扩大为页面重做。
5. 按7.1迁移受影响测试的规则读取位置，按7.2把品种指导正文接入现有模块核对任务；这两项属于文档正源迁移的配套，不新增任务或启用生产排程。
6. 迁移活跃引用，保留仍需使用的兼容跳转，验证承接后再归档状态清楚的旧方案。
7. 无论是否改变业务代码，都运行受影响的现有文档合同测试及核对输入测试，执行现有任务的 `--dry-run` 检查实际输入；同时验证目录、引用、规则承接和差异记录。涉及其他代码、配置或页面行为时，再补充与影响相称的测试和真实入口验证，结果写入原任务证据。

### 7.1 规则迁移时同步迁移现有合同测试

- 先定位直接读取旧文档或断言旧正文的测试。已知 `tests/test_xiaoxue_skill_contract.py` 中的 `test_profile_only_requests_do_not_pull_in_other_modules`，目前在 AGENTS 中检查完整的 LOL 画像展示规则；规则迁入 LOL 指导后，这项断言应读取新的正式位置。

- 同轮核对 `tests/test_project_module_contract.py` 中关于总入口、章节和兼容跳转的断言；共同规则仍检查 AGENTS，专项规则检查对应指导，导航检查指向正式来源。
- 即使本次只调整文档，也必须运行上述受影响测试。迁移前后结果分别记录，既有失败与本次引入的问题分开说明，不把旧失败声称为本次已解决。

### 7.2 让现有模块核对任务实际读取新指导

- 调整现有 `scripts/tasks/xiaoxue_project_center_module_review.py` 的 `build_packet()`。目前它只读取固定文件，不会沿 AGENTS 的 Markdown 链接打开新指导，因此必须把指导正文显式加入输入包的 `sources`。
- 该任务当前核对整张 `development_map`，应读取四份品种指导，并以各自完整相对路径作为来源标识；已有总规则、合同和状态证据继续保留。日常对话仍按相关品种读取，不因此要求每次加载全部指导。
- 在现有 `tests/test_project_center_content_coverage.py` 的输入包测试中验证：四份指导的来源均存在，内容与当前正式文件一致；核对结果可以引用这些来源，虚构来源仍被拒绝。只检查路径字符串或非空内容不足以证明读到了正确正文。
- 实施后运行现有任务的 `--dry-run`，逐项核对 `packet.sources` 中的指导正文与磁盘文件一致，并记录证据。该检查不调用模型、不写回页面、不创建或启用生产排程，也不代表模型判断效果已验收。

### 7.3 完成条件

文档整理完成应满足：

- 从 AGENTS 能进入四份指导；处理一个品种时能仅凭总规则和该指导理解业务要求，不必先遍历历史材料。
- 四份指导各自完整回答六个主题，说明现实能力和边界；核心业务文档数量为当前的“一加四”。
- 任一有效要求有可定位的正式来源；历史方案不再与现行指导并列生效，目录索引和活跃链接没有迁移造成的断链。
- 迁移后的现有合同测试仍保护原业务含义，能够从正确的正式位置读取规则；仅改文档也已完成相应检查。
- 现有模块核对任务的输入包实际包含四份指导的当前正文，相关输入测试和 `--dry-run` 已核对，不以 AGENTS 中出现链接代替读取证据。
- 技术地图、合同、配置、专业方法和真实数据仍保留原职责，指导没有复制第二套实现或假造缺失能力。
- 未完成的验收和实现差异仍可找到，没有用“文档整理完成”代替“足球体验已解决”或“整个项目已可用”。
- 保留现有未提交改动和回退证据；正式 `dist/`、生产服务、调度、模型、权限和真实业务数据不因本次文档整理而被改动。
