# 《小雪模块归并 PRD》修改意见

> 评审日期：2026-10-25（Asia/Shanghai）  
> 评审对象：`/home/ubuntu/.codex/attachments/2aa52d28-2b65-4ca4-a944-d7218b6e4cd2/小雪模块归并-PRD.md`  
> 本文件用途：评审附件方案，不授权执行其中的删除、迁移或生产改造。

## 一、结论

这份 PRD 的方向基本正确，但目前还不能直接作为施工单执行。

它正确地看到了项目存在重复登记、用户分类与后端实现层次交叉、兼容模块占据阅读面积等问题；“先处理明确废弃物，再归并 team、match、knowledge、facts”的顺序也合理。

但是，它把用户能力模块、后端实现模块、接口数量和 MCP 工具数量混在了同一个目标里。需要补充当前基线、迁移矩阵、兼容策略、回退方式和真实用户路径验收后，才能交给任何开发 harness 实施。

## 二、附件中的指令与本次评审请求要分开

附件中的“删模块、20 → 8、删除接口、跑验收”是 PRD 内部的待执行方案，不是本次用户请求对 Codex 的施工授权。

本次只完成两件事：

1. 判断这份 PRD 是否合理。
2. 为以后交给 DeepSeek harness 维护项目准备独立的交接说明。

本次不删除代码、不迁移数据库、不改生产服务、不修改业务数据。

## 三、当前代码基线核对

以下是按当前工作树静态核对得到的事实：

| 项目 | 当前观察 | 说明 |
|---|---:|---|
| 后端模块目录 | 20 | `xiaoxue_api/modules/*` 中可发现 20 个目录 |
| 项目级用户模块合同 | 8 | `config/module-contract.json` 中登记 8 个模块 |
| API 路由装饰器 | 129 | 对当前后端源码静态计数 |
| MCP 工具装饰器 | 48 | `scripts/hermes/xiaoxue_product_mcp.py` 静态计数 |
| 唯一 MCP | 1 | `xiaoxue-product` |
| 稳定后端入口 | 1 | `main.py` → FastAPI |

因此，“20 个后端模块”和“8 个项目模块”不是同一层。它们不能不加说明地直接做 20 → 8 的一对一替换。

## 四、哪些判断是对的

### 1. 需要减少重复维护

同一能力同时出现在项目合同、manifest、前端 loader、项目中心树、方法配置和文档中，确实会增加漂移风险。

正确目标应是：确定唯一正源，其余内容由它派生或只保留必要的适配信息。

### 2. team、match、knowledge、facts 是合理的归并候选

这些归并可以减少用户理解的对象数量，但归并后仍要保留内部职责差异。例如：

- 队伍画像、TS、首发是相关内容，但不是同一种事实。
- 普通 TK 和交易 TK 可以共享资料库，但不能合并语义。
- 当前比赛和长期知识可以关联，但临时观察不能自动写成长期结论。

### 3. 兼容层应退出日常入口

`market_notes`、`legacy_trades`、旧研究入口等可以评估是否退出主导航和默认阅读面，但“退出日常入口”不等于“立即删除目录和接口”。

## 五、需要修改的关键问题

### 1. 把“用户模块”和“实现模块”分层写清楚

建议把目标改成：

> 用户侧保持 8 个能力域；后端内部按所有权归并实现模块，但允许一个能力域由多个内部子模块组成。

不要把“8 个用户模块”强行变成“8 个 Python 目录”。后端模块是否合并，应由数据正源、写入边界和消费者决定。

### 2. 不要把数量作为主要完成标准

“路由 129 降低”“MCP 工具降到 20 以内”只能作为观察指标，不能作为成功条件。必须增加：

- 原有用户主路径保持可用。
- 正式数据行数不变。
- 保留的 API 和 MCP 调用语义不变，或有明确兼容转换。
- 删除项有消费者核对记录。
- 每个归并模块能从正式入口读回。

### 3. 修正 football 的范围表述

当前项目合同中足球仍是 `planned`，当前路线仍以 LOL 日常主路径为主。PRD 可以把 football 作为已登记的独立对象，但不能把它写成当前已经完成或必须随本轮归并上线的主模块。

### 4. 把删除步骤改成“退役评估 → 兼容期 → 删除”

每个准备删除的模块都要先列出：

- 代码消费者。
- 前端入口和深链。
- MCP 工具调用方。
- 历史数据是否仍需读取。
- 是否只读兼容。
- 替代入口。
- 回退方式。

没有这些证据，不能直接删。

### 5. 修正“四处 0 差异”的验收

合同、manifest、方法配置和能力树承担不同职责，不能要求结构完全一致。应改为：

- 每个用户能力都能找到唯一正源。
- 每个实现模块都能说明归属的用户能力。
- 映射不存在孤儿、重复所有权或未声明兼容项。
- 变更后由脚本检查映射完整性。

### 6. 增加迁移矩阵和回退要求

每个归并项必须有一行迁移记录：

| 旧模块 | 新归属 | 数据正源 | API | MCP 工具 | 前端消费者 | 测试 | 兼容策略 | 回退方式 |
|---|---|---|---|---|---|---|---|---|

没有填完的模块只能标为 `待核验`，不能标为完成。

## 六、建议的修正版实施顺序

### 第 0 步：冻结基线

记录当前模块、路由、MCP 工具、测试结果、页面入口和数据行数。明确当前工作树中的未提交改动不属于本轮归并，或逐项纳入范围。

### 第 1 步：只处理明确退役物

先从默认入口移除明确不再使用的兼容展示；保留只读兼容路径，直到消费者核对完成。

### 第 2 步：试点归并 team

合并展示和项目中心视图，暂不删除底层子模块。确认队伍画像、TS、首发和相关 TK 的真实读取都没有改变。

### 第 3 步：归并 match

统一当前赛事与单场工作区的用户入口，但保留单场记录、资料收集和判断各自的内部边界。

### 第 4 步：归并 knowledge 与 facts

先统一读取和索引，再评估旧实现是否可以删除。普通 TK、交易 TK、外部事实和英雄静态资料不能因为名称接近而混为一类。

### 第 5 步：更新项目中心和派生检查

让项目中心展示 8 个稳定用户能力域，内部实现清单另行作为开发视图，不把后端目录直接暴露给用户。

## 七、修正版验收标准

完成判断至少需要同时满足：

1. 用户能力域数量和边界明确。
2. 目标模块的正源、读写入口、兼容入口和消费者都有记录。
3. 相关 Python 测试和前端测试通过。
4. `python3 -m py_compile main.py` 通过。
5. 前端使用独立 `outDir` 构建通过，不覆盖正式 `dist`。
6. `/api/health`、项目模块接口和受影响 API 能读回。
7. 页面主路径与改造前行为一致。
8. 业务数据库表结构和业务数据行数未发生未授权变化。
9. MCP 工具发现和受影响命名工具能真实调用，或明确记录环境缺口。
10. 删除项有回退点，未验证部分没有被写成“已完成”。

## 八、最终意见

这份 PRD 可以保留作为“模块归并方向”，但应先按本文件补齐后再执行。最重要的修改不是把数字改小，而是把“用户概念收敛”和“后端目录重组”拆成两个层次，并为每个删除或归并动作增加消费者证据、兼容策略和回退方案。
