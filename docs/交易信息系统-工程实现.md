# 小雪交易信息系统｜系统设计与一次性重构方案（SSD）

> 这是给工程执行者看的唯一 SSD。它负责把 PRD 落到 Hermes、飞书、SOUL、Skills、工具、MCP、FastAPI、数据、追踪、部署与验收。当前能力是否可用仍以 `CURRENT-CAPABILITY-MAP.md`、真实运行证据和本文的缺口登记为准；本文不把设计目标提前写成完成状态。

## 当前 SSD 结论

本次工程目标是一次性完成统一骨架，而不是继续围绕某一个游戏做最小 MVP。施工前先完成现有能力盘点、内容映射、数据正源核对和缺口登记；代码、配置、数据和运行服务暂不因本文自动修改。

### 目标系统分层

```text
用户结果与决定权
  人：提出目标、判断、决定写入和交易
  小雪：统一入口，选择能力，组织证据，解释缺口
公共产品主干
  信息 → 普通 TK / 交易 TK → 当前判断 → 结果 → 复盘与校准
交易对象适配层
  LOL / CS / 足球 / 其他：主体、事件、信息源、结果源、专业方法
工程与数据地基
  正源、原始资料、工作状态、用户内容、索引镜像、Web 与观察面
```

### 公共内容模型

| 内容身份 | 负责什么 | 能否自动升级 | 正式边界 |
|---|---|---:|---|
| 原始资料 | 保存外部原文、接口响应、用户提供材料及来源时间 | 否 | 不冒充事实、TK 或判断 |
| 基础事实 | 对象、事件、赛程、阵容、赛果等可核对内容 | 否 | 只能由对应事实正源刷新或修正 |
| 系统整理 | 对资料做结构化摘要、关联和检索 | 否 | 必须可回查依据 |
| 普通 TK | 长期知识、规律、画像、方法和对象理解 | 否 | 用户确认后长期复用，不直接表示交易动作 |
| 交易 TK | 带适用条件、交易含义、反例和失效条件的交易认识 | 否 | 用户明确确认后写入；不是自动交易指令 |
| 当前情境 | 当前比赛、对象、焦点、临时观察和变化 | 否 | 可暂停、恢复、追溯，不自动进长期库 |
| 用户判断/交易记录 | 钧钧当时的判断、选择、盘口观察和备注 | 否 | 保留原话和身份，不改写为客观事实 |
| 结果与复盘 | 赛果、结算、原判断对照和校准材料 | 否 | 反馈给用户决定，不自动改 TK |
| 索引与展示镜像 | 搜索、Wiki、日报、Web 投影 | 否 | 从正源重建，不能反向覆盖正源 |

### 交易对象包合同

新增 LOL、CS、足球或其他对象时，只增加以下适配内容，不复制公共主干：

1. 对象定义、主体和事件；
2. 信息分类与信息源；
3. 结果分类与结果源；
4. 对象专属专业方法；
5. 普通 TK 和交易 TK 的适用范围；
6. 当前判断所需字段和市场表达；
7. 展示、检索、导入和复盘适配；
8. 已有内容、缺口、来源状态和真实旅程。

缺少其中一项时记录缺口，不修改公共 Agent Loop，不用模板伪造内容。新增资料或方法属于内容补充；只有公共契约、正源或能力真的缺失时，才进入代码改造。

新资料先作为原始信息接入，新方法先作为对象专业方法接入；两者都可以在不改公共字段、页面和主流程的情况下进入对象包，之后再由用户决定是否沉淀为普通 TK 或交易 TK。

### 目标对应的具体方案

**目标一：选对已有内容与方法。** 先判断当前问的是解释认识、当前适用性、交易价值还是明确的新研究；这是理解问题，不是要求用户选菜单。TK 用于可复用认识，交易 TK 用于交易认识及其条件、限制；资料提供事实，专业方法负责检查证据。游戏、队伍、赛区、阶段都是标签，不增加 TK 类别。

从上文已指明的条目开始；没有明确条目时，使用主题及对象标签查相关内容，再读原文。候选检索结果不是结论。对同义问法沿用同一问题理解和标签，不把整句原样子串搜索当唯一手段；先取相关范围，再筛选主题。交易快读只服务交易相关问题；纯规律解释不强制读取盘口或拉全量交易条目。检索空结果时核对现有文档读路径；工具故障与确无内容分别说明。

**目标二：只补必要缺口。** 已有内容能解释问题时直接用，不默认重算统计。问“现在还能用吗”才核实会影响适用性的当前事实；问交易价值才核对实际价格、时间及风险；用户明确要求新研究或原依据确实不足时，才选择对应研究方法。每项补查都须能说明：它改变哪个判断；不改变本版答案的材料不查、不讨论。缺口补不了就给条件判断或明确暂不能判断，不硬给交易方向。

**目标三：稳定且可信地回答。** 原文中的有效范围、时间、反例、待核或失效说明必须进入判断。文件修改时间不等于证据时效；旧统计可解释历史倾向，不能自动代表当前状态。冲突条目不靠“更新得晚”裁决：指出分歧及证据差别，无法裁决就保留不确定性。固定 21.5 的既有认识可以解释，但实际盘口与赔率决定当前价值，不能混为一谈。

回答按问题给结论、关键依据、适用条件或限制、必要缺口，不强制固定长模板。解释认识不变成交易推荐；当前条件不足不假装已核实。同问题换说法，在相同事实下应选材与逻辑一致；新事实使结论变化时说明变化点，发现旧判断错误时直接纠正。

**目标四：依据能追问，下一轮能接。** 本次回答保留足够识别关键来源的条目标题/标识及必要来源时间；用户追问时能读回相应原文、区分 TK 认识与本次推断，资料依据能指向实际来源。正常回复不堆路径与内部字段。接续优先利用当前对话已有对象、依据和条件；拿不到上次回答或当时依据时明说，不能用最新 TK 假装历史版本。本版不建设快照、后台跟踪或持久恢复，也不自动将聊天写成 TK。

### 沿用与最小调整边界

- 直接沿用：飞书自然入口、TK 文档读能力、交易 TK 查询、只读快读、现有研究工具与交易方法。可运行不等于全部有效，逐项用真实对话验证。
- 必须调整：日常入口的问题理解优先级；专项方法中“按需使用”与“关键词强制全库研究/固定交易方向”的冲突；候选检索后读原文及核对适用性的使用方式；回答中依据与缺口的表达。
- 暂不改后端：现有过滤及文档读取可完成本 MVP 所需的可靠选材；新增只读候选脚本支持按主题/对象/条目 id 读取正源，仍不写 TK、不读取盘口。若后续量化或同义召回仍失败，再单独提出最小后端改动。
- 已修改入口路由、无畏契约专项方法与只读候选脚本；未修改已有 TK、数据库、模型、权限、网关或交易观点。不全库整理、不建设历史留存、不新建单场分析或自动交易系统。

### 真实对话验收记录（2026-10-11）

在小雪飞书新会话入口选实际存在的条目和来源，不造测试知识。记录用户实际收到的回答与此次读取来源；这属于交付证据，不是新增历史留存产品。

1. “这条规律是什么意思？”：直接解释已有认识、条件与关键依据，不重做全库研究、不强推交易。
2. “它现在还能用吗？”：沿用上一条，只补影响当前适用性的事实；若缺事实，说明缺口和条件边界。
3. “这有交易价值吗？”：分开认识倾向与价格价值；缺可靠价格不硬给入场判断。
4. 相同问题换三种自然说法：在事实相同的情况下相关条目、判断逻辑保持一致，不要求字面措辞相同。
5. 追问“依据是哪条，为什么和刚才不同？”：能指回实际原文和新事实；无前次依据时承认无法核对，不伪造历史。
6. 选含待核、冲突或失效说明的现有内容：这些限制确实影响回答，不只加一句免责声明；讨论后 TK 内容保持不变。实际验收：揭幕轮观察项被回答为背景级、不能直接判断交易价值；“PRX 被加价就买对面”被按上海校准的“暂缓＋双条件”拒绝机械套用；两种自然问法均回指同一交易 TK 条目。

每例须同时核对入口选择、实际读到的内容、是否补了无关材料、最终回答及只读边界。真实结果：小雪在新会话实际加载 `other-esports-markets`，读取交易 TK 原文；解释问题没有读取盘口，没有写入 TK；交易价值追问明确给出“不能直接判断”及四项缺口；冲突场景实际说明校准优先级和“不按更新时间选边”。飞书消息由真实入口投递并在群话题读回。API 成功或测试通过只是前置证据，不能替代上述用户可见结果。

## 4. 各层唯一职责

### 4.1 飞书与 Gateway

项目能力与 Agent 身份分离：项目合同位于 `config/project-contract.json`，Agent 适配位于 `config/agents/*.json`。飞书、Profile、SOUL 和 Bot 显示名属于适配层；现有 `xiaoxue-product` MCP 与 `xiaoxue_*` 工具名作为兼容命名保留，不构成项目能力绑定。

负责：

- 收发消息、附件和连续分段回复；
- 会话身份、队列、中断、恢复和投递；
- 平台级长度、流式显示和错误投递；
- 把同一会话 ID 传给追踪和临时上下文。

禁止：

- 复制电竞业务规则；
- 配置一套飞书专属固定工作流；
- 用平台配置覆盖根 Skill 的业务选择；
- 因渠道限制改变数据身份或写入权限。

### 4.2 Hermes 核心

使用 Hermes 原生 Agent Loop、工具注册、Skill 按需加载、会话、记忆、Gateway、插件和审批能力。除非证据证明是 Hermes 通用缺陷，不修改 Agent Loop。

Hermes 核心负责“让模型能思考和行动”，不负责小雪的电竞业务流程。

### 4.3 小雪 SOUL

SOUL 只保留：

- 小雪身份、人格和表达；
- 电竞范围和钧钧最终决定权；
- 事实不足时不伪造；
- 先选最贴近的 Skill；
- 规则改造、工程实现和跨层排障通常建议由小白统筹；小雪具备完整能力，具体由当前目标和钧钧选择；
- 高风险动作遵守系统边界。

SOUL 不保存：

- 具体工具清单；
- 比赛分析步骤；
- 数据库和路径；
- 某个模块的触发词表；
- 后端实现、部署和验收规则；
- Codex、Pi 等施工 Harness 的长期职责。

### 4.4 小雪根 Skill

根 Skill 是轻量能力目录和公共业务合同，负责：

- 识别当前目标属于哪类能力；
- 告诉模型有哪些能力及何时使用；
- 统一“语义意图 × 副作用等级”；
- 规定信息身份、来源、冲突、空态和回复原则；
- 选择一个或多个必要能力；
- 在专项任务时加载唯一最贴近的 Skill。

模型保持自治：对已有正源、范围明确、可读回的小范围变化，默认直接完成，不把每个字段变化升级成确认流程；只有结构级、批量破坏性或不可逆动作才进入人工干预。Skill 提供判断原则和风险边界，不规定固定状态机、审批脚本或对象专用入口。

根 Skill 不得继续承担：

- 39 个工具逐条硬编码操作手册；
- 一场比赛必须执行的固定节点链；
- 每种自然说法对应哪一个函数的完整映射；
- 后端字段、目录、脚本和 API 细节；
- 旧责任、旧前端和历史迁移全文。

目标是把根 Skill 从“产品程序说明书”缩回“能力导航 + 公共原则”。详细内容按需放入专项 Skill 或工具描述，不默认塞进每轮上下文。

### 4.5 专项 Skills

专项 Skill 只保存一种专业方法或高风险流程，例如：

- 纯十英雄阵容分析；
- 交易系统方法；
- 版本理解更新；
- 队伍画像刷新；
- TK 压缩；
- 阶段复盘；
- 知识导入。

专项 Skill 可以规定方法、证据和验收；只有结构级或不可逆风险才可以要求人工确认，但不能：

- 建立平行后端；
- 复制小雪身份和根 Skill 全文；
- 把一种方法变成所有对话的强制入口；
- 绕过产品工具写正式数据；
- 为普通只读能力增加固定口令。

队伍画像 Skills 只在明确要求画像、专项深挖、赢输法、核心、scouting 或 BP 倾向时加载；普通单场首轮不加载双方长画像全文。

### 4.6 产品工具

每个工具是一项独立动作，工具描述应让模型知道“它能做什么、有什么副作用、何时不该用”。

工具可以：

- 查询一种正式数据；
- 建立或读取一种临时上下文；
- 保存一种明确身份的内容；
- 执行一次明确外部搜索；
- 预览或提交一种高风险动作。

工具不可以：

- 在内部替小雪完成整套业务编排；
- 用有限短语列表决定完整自然语言意图；
- 返回超长的重复资料让模型再次解析；
- 失败后指示模型搜索目录、调用终端或猜脚本；
- 同时读写多个不相关正源；
- 把一个工具变成新的业务大脑。

### 4.7 `xiaoxue-product` MCP

MCP 是 Hermes 与产品后端之间的薄适配层。

当前文件约 1325 行、39 个工具，已经出现自然路由、聚合、外搜、资料档案、工作区和写入边界混合增长。改造目标不是简单拆文件，而是先收窄职责：

- 暴露工具 schema 和注解；
- 把工具调用转换为稳定 FastAPI 请求；
- 传递会话、用户、意图等级和副作用等级；
- 统一转换后端成功、部分结果、空态和错误；
- 不复制业务查询、聚合、来源裁决和数据写入逻辑。

唯一 MCP 原则保留，但内部可以按能力拆分模块后由一个入口注册。禁止新增平行 `xiaoxue-product-2` 或按业务另开多个产品 Server。

### 4.8 FastAPI 与能力层

FastAPI 是产品能力和数据边界的正式承载层，负责：

- 对象、事件、资料、用户内容、临时状态、结果和长期知识的数据合同；
- 能力注册、健康、启停和版本；
- 正源适配、事务、幂等、校验、审计、读回和回退；
- 独立能力组合所需的结构化查询；
- 对外统一成功、部分、空态、冲突、不可用和错误结构。

FastAPI 不负责：

- 小雪人格；
- 自然语言表达；
- 交易建议；
- 把所有模块写成一条固定状态机；
- 因前端方便而复制数据正源。

### 4.9 数据与记忆

必须持续区分以下身份：

| 身份 | 最低要求 |
|---|---|
| 正式事实 | 正源、对象、事件时间、当前状态 |
| 外部原始资料 | 来源、发布时间、获取时间、原文或地址、适用范围 |
| 小雪整理 | 引用的资料 ID、方法版本、生成时间，不冒充事实 |
| 钧钧内容 | 原始表达、内容类型、对象/事件、写入时间，不被改写成事实 |
| 临时工作状态 | 会话/事件、当前焦点、临时事实和观察，可丢弃 |
| 结果与复盘 | 实际结果、证据、对应原记录、确认状态 |
| 长期知识 | 适用时期、证据、状态、确认关系和正式正源 |

索引、Wiki、RAG、MemPalace、日报和工作台只能是读取或展示镜像，除非能力地图明确它们是该内容的正式正源。

### 4.10 开发观察面

- 用户原话与会话 ID；
- 实际加载的 Skill；
- 模型可见的能力集合；
- 每个工具的参数、结果、状态、耗时和错误；
- 是否外搜、是否写入、写入正源和读回；
- 上下文压缩、重复读取和超长结果；
- 最终回复、用户纠正和人工评分；
- 同一场景修改前后的对比。

观察面展示实际轨迹，不是拖拽固定流程的编辑器。它不能成为新的运行正源。

## 5. 公共能力合同

每项能力通过注册加入，不通过修改核心分支加入。能力最低声明：

| 字段 | 作用 |
|---|---|
| `id` / `version` | 稳定标识与兼容版本 |
| `purpose` | 对用户解决什么问题 |
| `examples` | 非穷举自然表达，仅用于帮助理解和测试 |
| `inputs` | 必填、可选、可由会话补齐的输入 |
| `effect` | `read / temporary / live_search / reversible_change / write / critical` |
| `reads` / `writes` | 正式正源、外部系统和禁止副作用 |
| `output_schema` | 成功、部分、空态、冲突、不可用、错误 |
| `source_policy` | 来源、时间、新鲜度和冲突处理 |
| `settings` | 可调整项、作用范围、默认值和撤销 |
| `dependencies` | 服务、数据、专项 Skill 和环境要求 |
| `health` | 可用、部分可用、暂停、冲突、失效 |
| `tests` | 合同、自然语言场景、副作用和真实入口验收 |

`examples` 不能成为 `_PHRASES`、`contains any(...)` 或同类最终授权门。自然语言意图由 Agent 根据当前消息和紧邻上下文理解，下游只校验副作用等级、对象、身份、确认上下文和正源边界。

## 6. 公共结果合同

所有产品能力返回同一外壳，最低包含：

- `status`：`ok / partial / empty / conflict / unavailable / error`；
- `summary`：供小雪快速理解的短摘要；
- `data`：结构化结果；
- `sources`：正源、外部来源和资料时间；
- `effects`：是否联网、是否写入、写入哪里；
- `readback`：写入后的正式读回；
- `gaps`：缺失、过期、无法核验和限制；
- `conflicts`：新旧内容、冲突点和影响；
- `error`：稳定错误码与内部建议，不直接暴露给钧钧；
- `trace`：能力、版本、会话和调用标识。

一个能力失败不得清空其他独立结果。聚合由小雪或一个明确的只读聚合能力完成，聚合不能暗中产生正式写入。

### 6.1 模型读取契约（2026-08-13 新增，防上下文膨胀）

公共结果合同（第 6 节）是**后端/审计/回读**用的完整外壳；**给模型（小雪）读取的工具返回必须走精简契约**，不得直接把完整外壳塞给模型。本契约来自 2026-08-12~13 实测教训：`get_team` 曾一次返回 11,719 字符，其中外部包装壳 5,847（status/summary/sources/effects/trace）+ tk_items 长摘要 3,503，真·画像只有 ~2,000；"今天比赛"批量拉 8 队直接撑爆上下文。

**强制规则（新 MCP 工具/新读取接口必须遵守）：**

1. **单次工具返回 ≤ 3,000 字符**。超出的场景必须拆分（单对象查询、fields/limit 参数、标题列表代替全文）。
2. **只读工具禁止在内部拉全量再过滤**。如 `get_team` 只取一队 TS，必须调单队接口（`/fundamentals/teams?team=X`），不得 `scope=all&limit=80` 全量后 next() 取一队。
3. **禁止给模型返回 `_read_result` 审计外壳**。status/summary/sources/effects/readback/gaps/conflicts/trace 由后端或审计消费；模型读取返回只含业务字段（如 `{team, profile, ts, trading_notes, related_knowledge}`）。
4. **列表场景返回标题/摘要而非全文**。knowledge/notes 类只回标题列表；模型需要全文时再单独调取。
5. **MCP 工具统一 `structured_output=False`**（FastMCP 装饰器），避免同一内容以 content + structuredContent 双份返回，token 翻倍。
6. **新增读取能力时必须同时提供"给模型读的精简版"和"给人/审计看的完整版"**；不允许只做一个并让模型吞完整版。
7. **压缩阈值相关**：大接口必须主动瘦身，不得依赖压缩线兜底。全局 compression.threshold 保持 ≥0.65。

**验收**：每个读取型 MCP 工具在新增/修改时必须实测返回字符数，超过 3,000 的需在改动记录里说明拆分理由。

## 7. 意图与副作用

| 等级 | 运行条件 | 后端保证 |
|---|---|---|
| `read` | 对象或问题能识别 | 无写副作用；空态不造数据 |
| `temporary` | 对象能识别或自然表示切换/暂停/恢复 | 只改可丢弃上下文，不写长期知识 |
| `live_search` | 当前语义明确要求新的外部、最新、新闻、实时核对或搜索 | 只读外部调用；记录来源和时间；不自动沉淀 |
| `reversible_change` | 修改目标和范围清楚 | 记录前后值、应用、读回、版本和撤销 |
| `write` | 写入意思、对象、内容身份和范围清楚 | 写入指定正源、审计原话、读回；普通聊天不写 |
| `critical` | 删除、迁移、批量覆盖、换正源、权限、安全、密钥、自动交易或公网发布 | 备份、当前动作确认、执行、审计、读回和回退 |

无法判断时只允许降级，不允许升级。工具错误不能转化成“请用户改说一句口令”。

## 8. 当前已知结构问题

以下是接管基线，不是对未提交实现的最终裁决：

1. 小雪根 Skill 已增长为长篇工具操作手册，包含大量具体工具映射、固定节点和过期责任描述，容易挤占上下文并替模型编排。

## 9. 改造顺序

### 当前执行口径：一次性重构，不按对象拆产品切片

当前正式顺序只有一条：

1. 保护现有工作树和运行事实；
2. 完成全项目内容与能力盘点；
3. 按公共内容模型和对象包合同完成迁移映射；
4. 登记每个对象的内容缺口，区分“补内容”与“改系统”；
5. 依据映射一次性调整受影响的 Skill、MCP、后端、数据合同和入口；
6. 从真实小雪入口做全面验收，确认已有内容可用、缺口可见、新对象可扩展；
7. 进入长期小改。

下面的 `F-000` 至 `F-006` 是此前工程记录中的检查分组和证据索引。它们可以作为内部核对项复用，但不再代表用户要逐个批准的产品切片，也不改变“一次性重构”的目标。

### F-000｜保护基线与建立观察（检查分组）

目标：先能证明修改前发生了什么。

- 固定当前分支、HEAD、merge-base、脏文件清单和回退包；
- 不执行 `reset --hard`、`checkout --`、`clean` 或全局格式化；
- 保存目标真实会话、辅助会话和当前配置快照；
- 建立最小真实对话回归集；
- 使用 Hermes Dashboard 或追踪钩子记录 Skill、工具、耗时、错误和副作用。

完成证据：能从一个用户原话定位到实际 Skill、工具、数据来源、写入和最终回复。

### F-001｜治理与分层收口（检查分组）

目标：先统一谁负责什么，不改业务数据。

- 收口小白、小雪、Hermes 和可选 Coding Harness 的责任；
- 清理未来 Agent 会读取的过期责任入口；
- 确定 SOUL、根 Skill、专项 Skill、MCP、FastAPI、数据和观察面的唯一职责；
- 建立公共能力、结果、意图和副作用合同；
- 把旧 E-001 八步路径降为回归场景，不再作为所有能力必须经过的用户流程。

完成证据：正式文档、项目入口和测试合同不再把固定工作流当成产品骨架。

### F-002｜小雪 Agent 层减重（检查分组）

目标：让 Hermes 真正负责选择能力。

- SOUL 缩回身份与边界；
- 根 Skill 缩回能力目录和公共合同；
- 具体方法留在专项 Skill；
- 工具描述提供清晰用途和副作用；
- Feishu 只启用小雪日常所需能力，开发 Skills 保持禁用；
- 删除重复路由、过期职责和同一规则多处复制。

完成证据：普通单场、赛程、TK、资料、记录和复盘的自然表达能选择正确能力，不依赖固定句式；首轮不加载无关长 Skill。

### F-003｜后端能力骨架（检查分组）

目标：形成可插拔能力，而不是新的大状态机。

- 定义能力注册和统一结果外壳；
- 将来源、空态、冲突、副作用、审计和读回放入公共核心；结构级风险才附加人工干预；
- 将 LOL 对象、事件和专业字段留在 LOL 适配层；
- 将正式正源访问放入独立适配器；
- 将 MCP 收窄为薄适配；
- 查询能力先迁移，保持旧接口兼容。

完成证据：新增一个只读能力不需要修改 Hermes 核心、根 Skill 大流程或多个平行入口；一个模块失败不拖垮其他模块。

### F-004｜逐项迁移现有能力（检查分组）

顺序按风险，不按用户固定流程：

1. 赛程、队伍、TK、盘口等只读能力；
2. 单场临时上下文和只读聚合；
3. 外部搜索与来源合同；
4. 钧钧笔记、资料、整理和交易记录写入；
5. 赛果与复盘；
6. 版本、画像、三维、TK 压缩等确认后长期知识维护；
7. 自动化、日报和后台供给。

每迁移一项，保留旧入口兼容，真实验证后再决定退役。不得一次删除旧正源或批量迁移真实业务数据。

### F-005｜真实飞书验收（检查分组）

目标：从钧钧实际手机入口证明，而不是本机辅助会话代替。

最低场景：

- 自然提到一场比赛；
- 连续追问并沿用上下文；
- 明确要求最新外部资料；
- 普通聊天不外搜；
- 保存一条钧钧内容并读回；
- 普通评价不自动保存；
- 新旧冲突并列，小雪建议身份清楚；
- 一个数据源为空仍返回其他部分；
- 切换、暂停、恢复比赛不产生长期写入；
- 高风险动作停在预览和确认。

完成证据：飞书可见回复、工具轨迹、正式正源读回和禁止副作用同时成立。

### F-006｜进入长期小改（重构后的常态）

结构性改造通过后，每次只处理一个真实问题：

- 从失败会话建立问题卡；
- 判断应改 Skill、工具、后端、数据还是权限；
- 修改最小正确层；
- 重放原话、同义表达和反例；
- 通过后加入回归集并保留版本点；
- 前端需求继续排队，直到后端和飞书主路径稳定。

### F-006a｜小雪可靠性整改（2026-08-11）

本整改以“同类问题不再靠人工发现”为完成标准。每项必须同时具备：唯一正源或归一化规则、写入/读取防线、回归测试、真实 API/MCP/飞书入口验收。

| 问题 | 根因修复 | 通过标准 |

| 赛果队序 | 赛果读取按双方无序匹配，日期/时间用于消歧 | 任意队序查询同场得到同一赛果 |

## 10.1 第三赛段 TS 表重做

第三赛段 TS 的正式数据链为：`matches`（第三赛段已完赛）→ `ts_stage_table.py` 逐场 TrueSkill 计算 → `ts_stage_snapshots` 底表 → `build_display` → `ts_stage_display` 展示层 + `ts_cycle_signals` 周期信号层 → `/api/fundamentals/teams` 的 `ts_display` → 前端 TS 表、赛区周期扫描、日报和单场分析。旧赛季位置权重、阶段加成、三维系数与胜率二次校准不再进入这条链。

- **L1 计算层**：只处理赛果和模型原始量。TrueSkill 逐场更新 `mu`、`sigma`，并得到 `ts = mu - 3σ`；庄家按 `mu` 开盘，预测看更保守的 `ts`。
- **L2 快照层**：`ts_stage_snapshots` 是第三赛段的持久底表，保存 L1 的阶段结果，供展示构建、日报和分析读取；原始量留在此层及数据处理层。
- **展示层**：`build_display` 从 snapshots 构建 `ts_stage_display`；周期分类从底表历史和展示层构建 `ts_cycle_signals`，再共同投影到 API 的 `ts_display`。前端和分析入口只读处理后的字段与周期信号；任何用户界面不得出现 `mu`、`sigma` 或原始 `ts`。

### 10.1.1 国际赛阶段（2026-09-30 扩展）

| 字段 key | 中文名 | 含义 | 计算方式 | 0–100 方向 | 消费方 |
|---|---|---|---|---|---|
| `power_score` | 综合实力 | 可用于横向比较的保守实力展示值 | 底表 TS 分经 60 分强弱分界的单调曲线拉差 | 100 = 最强；60 仍是强弱分界 | 前端 TS 表 / 日报 / 阵容分析 |
| `volatility_score` | 稳定性 | 结果兑现和被爆冷风险的稳定程度；不再叫“波动” | 底表行为稳定性分以 50 为中性线做对比度拉伸；不再直接复用 sigma | 100 = 最稳；50 = 中性 | 前端 TS 表 / 日报 / 阵容分析 |
| `trend` | 趋势 | 当前实力变化方向与斜率 | 将近期 velocity 按同赛区最大绝对值映射为 -100～+100 | 正=上行，负=下行；绝对值越大方向越明显 | 前端 TS 表 / 日报 / 阵容分析 |
| `momentum` | 势头 | 趋势斜率的变化阶段 | 将 acceleration 按同赛区最大绝对值映射为 -100～+100；前台展示阶段标签 | 不单独作为好坏分数；结合趋势读加速/钝化/启动 | 前端 TS 表 / 日报 / 单场分析 |
| `cycle` | 周期信号 | 已算好的赛区重点周期品种 | `ts_cycle_signals` 由 TS 历史、趋势、势头和震荡强度统一生成 | 类型=上行/下行/强震荡/横盘；阶段=初期/延续/末期/进行中；非空 `focus_signal` 才进入重点池 | 前端重点关注 / 赛区扫描 / 单队复核 / 单场分析 |
| `status` | 状态 | 将实力档与趋势方向合成的可读标签 | 实力档（强/弱）× 趋势（上升/回升/平稳/下滑），如“强·上升” | 不适用；标签不参与百分制 | 前端 TS 表 / 日报 / 阵容分析 |

### 分组折扣

`config/ts_group_discount.json`（schema：`ts_group_discount/1`）是唯一名单和折扣正源，`ts_stage_table.py` 只读取配置，禁止在代码中硬编码队伍或系数。LPL 涅槃组（NIP、IG、WBG、LNG）和 LCK 挑战组（BFX、BRO、DNS、KRX、NS）均按 `×0.8` 折扣；两类赛制均为组内单循环、无跨组。目标是让次级组头部约等于顶级组中部，而非因组内战绩直接顶到全赛区顶部；具体名单始终以配置为准。

## 10.2 能力交付合同：减少跨层改动漏链

对需要经过数据、API、Agent 和自动维护的能力，模块 Manifest 可选声明 `delivery` 合同：

1. `configuration`：唯一规则/配置拥有者；
2. `refresh`：唯一刷新入口及其自动化调用者；
3. `source`：唯一正源与快照；
4. `projections`：稳定 API 投影和必备字段；
5. `agent_entry`：小雪已有的自然使用入口及必备字段；
6. `acceptance`：快照读回、API 投影、Agent 工具读回、自动化入口四类检查。

合同用于发现“引擎改了、旧自动化/API/MCP仍在用旧链”的断裂；它不定义对话状态机、关键词路由、写入审批或小雪的分析顺序。小雪仍自主决定何时读取能力、怎样组合证据、怎样解释，以及对已有正源的小范围更新。

`fundamentals` 的 TS 投影字段固定为 `ts_display.power_score`、`volatility_score`、`trend`、`momentum`、`status`。`/api/fundamentals/teams` 与 `get_team` 对小雪提供这五项处理后的展示值；前端、日报、阵容分析和小雪的普通解释均不再消费或展示“实力分、稳定分、原始 mu、sigma、TS”这一旧 L2 字段集合。原始量只留给数据处理、审计与模型计算使用，字段解释以 10.1 的“TS 展示层字段含义表”为准。

首个试点是 `fundamentals` 的第三赛段 TS。统一验收入口：

`PYTHONPATH=/home/ubuntu/xiaoxue-web /home/ubuntu/.hermes/hermes-agent/venv/bin/python /home/ubuntu/xiaoxue-web/scripts/verify_capability_delivery.py fundamentals`

后续将首发、三维、画像、TK、版本理解按此合同渐进接入；新旧链先并行验证，正式消费者全部切换后才退旧链，不进行全量推倒重写。

自 2026-08-07 起，所有已注册模块均自动获得基线合同（规则拥有者、读写正源、Router、`xiaoxue-product` 入口、模块健康与 MCP 发现验收）。涉及定时刷新、正式数据快照、跨 API/MCP 投影或业务写回的能力必须升级为完整合同，并增加专属读回验收；TS 是首个完整合同。基线合同不会限制小雪自主选择能力、组合证据、解释结果或已有正源的小范围自治更新。

## 10.3 队伍画像统一维护合同

### 目标与正源

LPL / LCK 的长期队伍描述收口为唯一 `team_profile` 正源。它固定保存五个正文文本字段：`positioning`（队伍定位）、`win_path`（怎么赢）、`lose_path`（怎么输）、`key_points`（关键点）、`bp_tendency`（BP 倾向），以及正文外的 `updated_at`、证据引用和版本号。任何字段为空都表示资料不足，不能用泛化模板填充。

正文序列化格式固定为：

`# {队伍} 队伍画像`、`- 队伍定位：...`、`- 怎么赢：...`、`- 怎么输：...`、`- 关键点：...`、`- BP 倾向：...`

每项最多两句；正文不写 TK 原文、搜索过程、TS 数字、样本统计、更新时间、维护过程或“本期变化”。证据、来源、时间、冲突和资料覆盖放在正文外元数据中。

现有 `team_3d_data` 的三个字段不再接受独立业务维护：

| 旧字段 | 统一画像字段 |
|---|---|
| `优势局习惯` | `win_path`（怎么赢） |
| `劣势局习惯` | `lose_path`（怎么输） |
| `胜负手位置` | `key_points`（关键点） |

在迁移期保留旧读接口和表字段以兼容工作台及单场模块，但其值只能由唯一 `team_profile` 投影生成；不得继续让三维和画像分别成为可写正源。Wiki、队伍专项 Skill、工作台与单场资料都是该正源的读取/展示镜像。

### 小雪的全量维护执行合同

用户明确要求维护指定队伍、指定赛区或当前 LPL / LCK 全量时，小雪按以下边界执行，不向钧钧索要技术步骤：

1. 锁定范围、维护截止日和当前首发；全量范围只含当期 LPL / LCK 正式队伍。
2. 对每队读取旧画像、当前首发、当前赛段 TS / 样本，并检索维护期内该队相关 TK（含钧钧交易记录）。
3. 当现有材料不足以判断时，再检索近期战报或必要外部资料；外搜材料保留来源和时间，不自动伪装成正式事实。
4. 以旧画像为基线，将证据归入五项字段；删除重复叙述，保留可被比赛验证的因果描述。单条记录、未经验证的交易判断、过时阵容或相互冲突材料不能单独改写长期画像。
5. 对足以支持的结论写入唯一 `team_profile`；证据不足字段明确保留“资料不足，暂不下结论”，不凭空补齐。写入后读回五项字段和更新时间。
6. 由统一画像生成三维兼容投影并刷新 Wiki / 工作台镜像；镜像失败必须返回 `partial`，不能声称维护完成。

小雪的用户侧输出只展示最终五项画像与必要的资料不足提示；TK 列表、搜索过程、候选差分和迁移细节默认不展开。钧钧要求看依据时，才按条展示来源和原始记录。

### 迁移与验收

该能力在统一重构中作为一个迁移检查项处理，禁止把既有真实内容直接批量覆盖：

1. 先建立 `team_profile` 的唯一合同、读接口、写入读回和三维兼容投影，并用 BLG、GEN、HLE 三队把现有不同格式合成五项画像。
2. 验收三队：五项齐全；旧三维可从画像投影读到；专项画像/Wiki/工作台返回同一内容；首发和 TS 仍独立读取；无证据字段保持空或明确资料不足。
3. 钧钧从小雪入口发出“维护 LPL / LCK 全部队伍”后，再执行首次全量维护；不得把样板或迁移测试冒充为真实全量维护。
4. 全量完成后逐队读回，并报告已完成数、资料不足数、外搜失败数和镜像失败数；任何失败队保留旧画像，不用模板补位。

最低自动化回归覆盖：单队读、单队维护读回、资料不足、相互冲突、钧钧交易记录不被当作客观事实、三维兼容投影、LPL/LCK 全量范围锁定、镜像失败返回 `partial`，以及从小雪真实入口完成一次指定队维护。
