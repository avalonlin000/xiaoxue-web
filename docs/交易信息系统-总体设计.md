# 小雪交易信息系统｜产品需求文档（PRD）

> 这是给钧钧看的唯一产品正源。它定义统一骨架、内容归位、角色边界、扩展方式和完成标准；不要求当前所有交易对象的资料、方法和信息源已经齐全。代码结构、服务、接口、迁移和技术验证统一写在《交易信息系统-工程实现.md》。

## 0. 本次重构要解决什么

本次不是新增一个“交易 TK 产品”，也不是先做某一个游戏的 MVP，而是把现有小雪已经拥有的资料、普通 TK、交易 TK、比赛工作区、盘口记录、画像、版本理解、结果和复盘能力，统一放进一个可以长期承载内容的交易信息系统骨架。

重构完成后，钧钧可以继续补充信息、方法和交易对象；补充内容不应反复改动小雪的核心协作结构。当前缺什么要明确列出来，但缺口本身不阻塞骨架成立。

## 0.1 统一骨架

```text
人
  ↕
小雪（统一协作入口）
  ↕
信息与方法
  ↓
普通 TK / 交易 TK
  ↓
人的当前判断与交易决定
  ↓
结果与复盘
  ↓
TK 校准与新信息
```

- **人**：确定目标和边界，判断是否采纳，决定是否交易，决定是否修改长期内容。
- **小雪**：理解问题，选择和组合能力，整理信息，调用 TK，指出条件、反证和缺口，按明确意图保存和读回。
- **信息**：比赛、队伍、选手、版本、BP、地图、伤停、赔率、舆情、赛果和钧钧提供的材料。
- **普通 TK**：可复用的知识、规律、画像、方法和对象理解，不直接等于交易动作。
- **交易 TK**：经过提炼和验证、带适用条件、交易含义和失效条件的交易认识；不是自动交易指令。
- **当前判断**：某一次具体情境下的临时解释、应用和决定依据，不自动成为长期 TK。
- **结果**：实际赛果、市场结果、判断变化和复盘材料，必须回到当时依据再校准。

## 0.2 现有内容的统一归位

| 现有内容 | 统一归位 | 固定边界 |
|---|---|---|
| 队伍、选手、球队、球员资料 | 对象信息 | 保存对象事实和来源，不自动成为交易结论 |
| 版本、地图、赛制、联赛环境 | 对象知识 / 普通 TK | 作为分析背景，不直接等于交易机会 |
| 战术规律、比赛观察、方法论 | 普通 TK | 可复用但不自动带交易含义 |
| 带交易条件的认识 | 交易 TK | 必须能说明适用条件、交易含义和失效条件 |
| 赛程、阵容、BP、伤停、赔率、舆情 | 当前信息 | 保留来源和时间，不覆盖长期内容 |
| 单场工作区、`match_runs` | 当前情境与过程记录 | 可暂停、恢复和追溯，不自动写入长期 TK |
| 盘口记录 | 人的当前判断 / 交易记录 | 保存钧钧原始判断，不自动升级为交易 TK |
| 赛果与结算 | 结果 | 只提供反馈，不自动修改 TK |
| 阶段复盘候选 | TK 校准材料 | 经用户判断后才进入普通 TK 或交易 TK |
| 日报、外部搜索和导入资料 | 信息输入 | 不冒充事实、判断或长期知识 |
| Skills、MCP、后端和前端模块 | 小雪的能力组件与观察面 | 服务统一协作入口，不定义用户必须走的流程 |

## 0.3 内容不完整也可以成立

每个交易对象都按同一份对象包合同接入：对象定义、主体和事件、信息源、结果源、专业方法、普通 TK、交易 TK、当前判断字段和展示/检索适配。某一项暂时没有，只登记为缺口，不为填表伪造内容，也不因此重写公共骨架。

因此，LOL、CS、足球可以共用同一套协作、TK、结果和复盘机制；它们只补各自的对象资料、信息源、专业方法和交易认识。新增交易对象是增加对象包，不是复制一套小雪。

找到新资料时，可以先按原始信息放入对应对象；找到新的思考方法时，可以先按对象方法补入。两者都不要求先修改公共字段、页面或主流程，后续再由小雪和钧钧决定是否整理成普通 TK 或交易 TK。

项目中心提供“系统结构图”和“交易对象目录”两个用户视图：前者说明人、小雪、信息、普通 TK、交易 TK、当前判断、结果与复盘的关系；后者显示 LOL、CS、足球等对象的状态和缺口。两者都读取项目合同和运行接口，不另建手工架构事实。

## 1. 已确定的产品目标

小雪是钧钧长期使用的个人电竞交易助理，当前主业是 LOL。

她负责获取、保存、整理、关联和找回真实信息，也可以基于证据给出自己的建议；她不替钧钧自动交易，不把建议冒充事实，最终判断和交易决定始终由钧钧完成。

产品当前以手机飞书为主要入口。钧钧只需要正常聊天，不需要学习工具名、命令、口令、数据库或固定步骤。

小雪与小白都具备整个项目的能力；差异只在 Profile、模型和开发类 Skill 配置。小雪是正式业务与日常使用窗口；小白是开发统筹窗口。钧钧通常建议把架构、代码、数据排查、部署、验证和大范围改造交给模型更强、开发类 Skill 更齐的小白统筹，但小雪也可以按当前目标直接处理。使用什么 Coding Harness 只是小白后台的施工选择，不属于小雪产品，也不能决定小雪怎样思考；日常使用继续由小雪入口承接。

## 2. 房子的骨架

小雪不是固定流水线。产品只搭一套稳定骨架，具体怎么使用由小雪根据当下目标决定。

这套骨架只有五部分：

1. **Hermes 大脑**：理解对话、选择能力、组织执行、维持会话和记忆。
2. **小雪身份与方法**：限定她是谁、负责什么、有哪些电竞方法和业务边界。
3. **可组合能力**：赛程、队伍、TK、资料、阵容、市场、记录、复盘等能力可以独立使用，也可以临时组合。
4. **真实数据与来源**：外部资料、正式数据、小雪整理、钧钧内容、比赛状态、赛果和长期知识分别保存，不能互相冒充。
5. **安全边界**：读取和临时整理尽量自然；已有正源上的小范围业务更新默认自治并读回；结构级改造、批量破坏性动作、删除、迁移、权限、密钥、发布和不可逆动作才按影响程度确认。

房子的骨架不能规定钧钧必须先进入哪个房间，也不能替小雪预先写死每一次调用顺序。

## 3. 小雪应该怎样工作

### 跨游戏的交易 TK 生成与管理过程（已认可，工程接入待验收）

过程轴由五种工作阶段构成，游戏轴承载 LOL、无畏契约、CS 的专业规则；两轴可组合，不以赛前、赛中、赛后的时间顺序强制编排。

1. **发现与研究**：核实事实、换坐标比较、寻找原因、竞争解释及反例。探索不必产生 TK。
2. **提炼与验证**：检验是否能提前识别和重复使用，明确适用条件、信号、行动与改变判断的条件；区分比赛规律和当前价格下的交易机会。站得住的结论才沉淀为交易 TK。
3. **情境应用**：结合当前环境、对象与价格调用 TK；不机械套用，也不把相关证据重复计票。给方向、行动条件或需要观察的信息。
4. **动态跟踪**：用新事实更新当前情境解释与行动判断。阵容、版本、赔率、局内信息均可触发重看；单场波动不直接改写长期 TK。未实现监测时，只在用户追问或实际取得新信息时继续，不承诺后台提醒。
5. **结果校准**：对照当时依据，区分事实计算、解释、适用范围、交易选择错误与合理判断的不利结果；按证据保留、补充、修订或暂停 TK，也可以回到研究。

五阶段是小雪识别问题、组合能力的方法，不是五个必填表、五个页面或强制流水线。钧钧可从任意自然语言问题进入、切换、回溯，无需知道阶段名称。

普通 TK 与交易 TK 都是长期内容，但职责不同：普通 TK 保存知识、规律、画像、方法和对象理解；交易 TK 保存经过交易条件约束的可复用认识。交易 TK 是交易判断的正式认知载体，但不是自动交易指令。研究材料、统计结果、当前情境和单场记录只支撑追溯，不自动升级为任何长期 TK。事实、预测与当前价格下的交易价值必须分开，缺可靠价格不声称盈利优势。

无畏契约、LOL、CS 等已有样本都只是现有内容和能力的验证材料，不再作为整个产品的首个 MVP 或唯一施工入口。当前任务是先完成统一骨架和内容归位，再按缺口补信息、方法和对象包。

### 交易 TK 的核心对象与首版范围（钧钧认可的骨架）

交易 TK 是可复用、可验证的交易认识，不是一条下注记录，也不是泛泛游戏知识。内容应讲清认识、适用条件、识别信号、交易含义、依据与反例、改变判断的条件；这是语义骨架，不是六个必填框，也不预先规定数据库字段。

- 支撑材料：原始资料、比赛事实、统计和游戏知识保留各自来源，作为 TK 的依据，不冒充正式交易结论。
- 当前应用：记录某次情境如何使用 TK、当时依据、价格或价格缺口、判断及后续变化；不自动成为新 TK。
- 正式交易 TK：值得持续使用和检验的认识，沿用既有 TK 正源，不另建结论库。普通聊天、资料获取和单场暂存不等于正式写入。
- 跨游戏共享语义结构与基础能力，不强行共享规律。游戏专属 TK 保留适用范围；没有跨游戏依据，不扩大为通用结论。
- 一条 TK 可以应用于多个情境，一个情境可以引用多条 TK。应用必须能追溯当时使用的内容与依据；后续修订不能改写过去的判断。具体版本或快照机制留给工程方案。
- 校准区分认识、适用条件、交易选择或价格问题与合理判断的不利结果，不以一次输赢直接升级或否定长期 TK。

本次不设按单个游戏拆分的产品 MVP。用户可见验收以“现有内容能否在统一骨架中被正确使用、缺口能否被单独补充、新对象能否按合同加入”为准。自动赛程与价格接入、后台实时跟踪、自动交易、自动修改 TK、收益率排行榜、前端整体重做和新建平行 TK 库均不属于公共骨架。

### 3.1 自然理解

钧钧说“聊聊明天 HLE 打 GENG”，小雪应直接理解正在谈一场比赛，读取已有内部信息并建立可丢弃的临时上下文。

她不能要求钧钧再说“执行、调用、打开、开始分析、继续”等标准句式。所有业务模块都遵循同一原则，不能每个工具维护一套暗号。

### 3.2 自己选择和组合能力

小雪根据当前问题决定：

- 要读取哪些内部资料；
- 是否只需要一个能力，还是组合多个能力；
- 先看什么、后看什么；
- 哪些内容已经足够，哪些内容应明确留空；
- 后续追问应该沿用什么上下文；
- 什么时候只回答，什么时候调用工具。

大方法可以限定观察角度、证据要求和风险边界，但不能变成每次都要执行完的固定清单。

### 3.3 交易分析怎样使用

交易分析默认由聊天推进，前端只做查看、记录、回看和确认：赛前、赛中、赛后是一场比赛内的同一条临时线程；赛段框架只在明确讨论当前周期或本场确实需要阶段背景时使用；赛后只有可复用结论进入沉淀候选。交易总纲、周期与实力判断、队伍与版本、BP 与阵容、赛后校准是可按需调用的方法，不是要求钧钧学习或逐项完成的流程。

### 3.4 一次给够当前需要的信息

单场比赛首次展开默认采用两层展示：

- **结论地图**：很短地说明比赛身份、当前最可靠信息、主要矛盾、值得观察的变量和最大资料缺口。
- **完整分区**：继续展示比赛、双方、版本、长期知识/TK、已保存外部资料、市场/交易记录、冲突、缺口、来源和时间。

这只是阅读组织方式，不是执行步骤。平台长度不够时可以自动分成连续消息，但不能要求钧钧回复“继续”才能看完。

### 3.4 事实、建议和决定分开

小雪可以给出“当前更值得关注什么”的建议，但必须同时说明：

- 依据是什么；
- 来源和资料时间是什么；
- 把握有多大；
- 哪些新证据会改变建议。

新资料与旧画像、旧 TK 或旧版本理解冲突时，新旧并列展示。小雪不能偷偷折中、覆盖旧内容或把冲突写成已经解决。

钧钧的判断单独保留，不能被改写成客观事实、小雪结论或长期知识。

### 3.5 缺数据时不装懂

某一项为空不能阻断其他结果。小雪应先给能确认的部分，再明确说明缺什么、过期风险是什么、当前无法核验什么。

只有缺失信息会改变对象、正式写入归属、外部调用或实际结果时，才问一个自然问题。不能为了方便内部工具而追问。

## 4. 能力怎样增加

以后新增能力采用“插入新积木”的方式，不重写小雪核心。

一项新能力至少要说明：

- 它能帮助钧钧完成什么；
- 什么时候适合使用；
- 需要哪些输入；
- 会读取和写入什么；
- 是否会联网或产生副作用；
- 成功、部分结果、空态和失败分别怎样表达；
- 怎样验证和撤销。

优先顺序是：

1. 现有能力已经足够，只补充方法说明；
2. 需要新的业务方法，增加或调整 Skill；
3. 缺少真实动作能力，增加一个独立工具或后端模块；
4. 只有涉及公共能力时才调整骨架。

新增足球、股票或其他分类时，复用相同的信息、记忆、权限、来源、复盘和审计骨架，只增加该分类自己的对象、事件、数据和专业方法。

## 5. 统一的动作边界

小雪按“真实意思 × 动作后果”判断，不按关键词白名单判断。

| 动作 | 默认处理 |
|---|---|
| 回答、读取内部资料、整理已有信息 | 对象和目标能识别就直接完成 |
| 建立、切换、暂停、恢复临时上下文 | 自然表达清楚就执行，不视为正式保存 |
| 新的外部搜索 | 只有当前语义明确要求最新、外部、新闻、实时核对或搜索时执行 |
| 可恢复设置 | 修改目标和范围清楚就执行，说明影响和撤销办法 |
| 正式保存、更新、发布 | 写入意思、对象、内容身份和范围清楚后执行，完成后读回 |
| 删除、迁移、权限、安全、密钥、自动交易等高风险动作 | 先展示对象、影响和恢复办法，再取得这一次动作的确认 |

无法确定时，统一降到更低副作用：能只读就只读，不自动联网、不正式写入、不执行高风险动作。

## 6. 当前 LOL 能力范围

当前能力按用途组织，不按强制顺序组织：

- **对象和事件**：队伍、选手、赛程、比赛、首发、换人、版本变化、BP、市场变化和赛果。
- **资料和长期理解**：带来源原始资料、小雪整理、队伍画像（已包含原三维）、版本理解、普通 TK 和交易 TK。
- **专业分析**：纯十英雄阵容、TS/波动、战术视角、队伍版本适配和交易系统方法。
- **当前比赛**：临时比赛上下文、当前焦点、已确认事实、临时观察和变化。
- **钧钧内容**：个人笔记、疑问、判断、盘口与交易记录。
- **结果与复盘**：实际赛果、原记录对照、复盘和待确认长期认识。

### 6.1 模块化使用合同

用户可见模块不是文件夹或数据库表，而是一条能被自然使用、写回、读回和继续使用的能力闭环。项目模块 ID、显示名、正源、入口、普通写回、读回、消费者、字段映射和兼容名的唯一事实源是 `config/module-contract.json`；给小雪按需读取的完整产品语言说明是 `docs/小雪项目总使用说明.md`。本文件只保留产品目标和边界，不复制那两份合同正文。

TS／队伍实力展示、队伍画像／首发／队伍资料、TK／交易记录、当前赛事／单场工作区、版本／方法／阵容分析、日报／知识维护、知识维护与自动化后台、关注队伍／赛事配置都复用同一套“自然进入 → 正源读取 → 必要时普通写回 → 正式读回”的骨架。它们可以组合，但不互相冒充；例如纯阵容不带入 TS 或盘口，当前工作区不自动成为长期知识，后台任务不成为用户固定流程。

纯阵容分析只分析十英雄和通用版本知识，不能偷偷带入队伍、选手、TS、盘口、当前经济或赛果。交易判断可以把纯阵容结论作为一个输入，但必须另外核对队伍、市场、趋势、分歧和风险。

## 7. 日常使用与开发改进

钧钧继续在手机飞书使用小雪，不需要操作开发工具。

边用边改的固定循环是：

1. 钧钧正常使用并指出哪里不自然、错误或死板。
2. 小白从真实会话和执行轨迹判断问题属于方法、Skill、工具、数据、记忆、权限还是框架。
3. 只修改正确的一层，不靠增加口令和单句特判掩盖问题。
4. 在隔离测试会话重放原话和不同说法，检查结果与副作用。
5. 通过后再进入正式飞书使用；失败时保留原版本和回退位置。
6. 已验证问题加入真实对话回归集，防止以后重新变坏。

开发页面的作用是让小白看见每轮实际使用了什么 Skill、工具、数据、时间和错误；它不是让钧钧拖拽固定流程，也不能反向控制小雪必须怎么思考。

## 8. 本次一次性重构

本次重构一次性完成“统一骨架 + 现有内容归位 + 缺口登记 + 对象扩展合同”，不按 LOL、CS、足球拆成多个产品切片。

重构必须覆盖：

1. Hermes、飞书和小雪的统一协作职责；
2. 普通 TK、交易 TK、当前判断、结果与复盘的内容边界；
3. 现有资料、画像、版本、比赛、盘口、日报、Skill、MCP、后端和前端能力的唯一归位；
4. 信息源、结果源、专业方法和对象包的接入合同；
5. 每个对象的已有内容、缺失内容和后续补法；
6. 正源、写入、读回、冲突、空态、失败和回退的公共规则；
7. 旧固定流程、重复规则、历史兼容入口和过期责任描述的处理决定。

本次完成不要求 CS 或足球资料已经齐全，也不要求立刻补齐缺失方法。缺口必须可见、可登记、可独立补充，不能因为缺内容而修改公共骨架。**本轮不做产品前端重做**，现有 Web 保持当前用途，不新增第二套业务逻辑。

## 9. 大改后的持续小改

结构性改造完成后，项目进入长期小步迭代：

- 一次解决一个真实使用问题；
- 新能力优先作为独立积木加入；
- 修改前有真实失败证据，修改后重放同一场景；
- 不因为一个例句失败就增加一句硬编码；
- 不因为一次成功就宣称所有模块完成；
- 重要修改保留版本、证据和回退位置。

## 10. 当前完成标准

本次重构只有在以下结果真实成立时才算完成：

- 现有内容已完成统一归位，并且每项内容有身份、正源、读取方式和写入边界；
- 普通 TK 与交易 TK 的语义、写入门槛、调用方式和展示口径不同且可追溯；
- 小雪能根据问题判断当前缺的是信息、知识、方法、交易应用还是结果复盘，并组合已有能力；
- 当前判断、盘口记录、单场状态和赛果不会自动升级或覆盖长期 TK；
- 每个已有交易对象都有内容盘点和缺口清单，缺口不会被伪造内容填平；
- 新信息、新方法和新交易对象可以通过既定合同加入，不修改公共协作骨架；
- 现有入口、历史内容和兼容能力没有因归位而丢失，冲突和未验证状态明确可见；
- 至少一条真实小雪主路径证明“读取已有内容 → 组合判断 → 明确缺口 → 用户决定写入或不写入 → 结果可回溯”；
- 代码施工前的文档、映射和缺口登记已经完成；文档完成本身不冒充运行态完成。

当前能力是否已经可用，仍以《CURRENT-CAPABILITY-MAP.md》和真实运行证据为准；本文件不把目标提前写成完成状态。

## 11. LPL / LCK 队伍画像统一

钧钧维护队伍的目标，是长期知道“这队现在是什么队”，而不是分别维护一份三维标签和一篇画像。自本设计生效起，LPL / LCK 每支队伍只维护一个正式对象：**队伍画像**。

### 11.1 用户看到的唯一内容

每队固定五项，正文严格使用以下格式，不增加“本期变化”、材料统计、维护过程或额外小节：

# {队伍} 队伍画像

- **队伍定位：**一句话说明这是什么队、主要靠什么赢。
- **怎么赢：**一句到两句说明从前期到中后期最常见的取胜路径。
- **怎么输：**一句到两句说明打法被什么限制、最容易在哪种情况下失效。
- **关键点：**一句到两句说明看谁、哪条线或哪种联动，就能判断这队能不能按自己的方式打。
- **BP 倾向：**一句到两句说明适合什么阵容/对局环境，最怕什么限制。

正文只写当前队伍结论，不把 TK 原文、搜索过程、TS 数字、样本统计、更新时间或维护说明塞进正文。每项最多两句；证据、来源、时间和冲突放在正文外的元数据中。资料不足时只在对应项写“当前证据不足”，不使用泛化套话补齐。

一个人打开任一队的画像，应能立刻知道它是什么队、怎么赢、怎么输、看什么、BP 往哪边走。

### 11.2 原三维和旧画像如何合并

旧 `优势局习惯` 合并进“优势局怎么打”；旧 `劣势局习惯` 合并进“劣势局怎么打”；旧 `胜负手位置` 合并进“核心与胜负手”。旧画像的“一句话结论、怎么打、常见赢法、常见输法、核心是谁、BP 倾向、对手破解”按语义归入同样五项。合并时去重，不把两份旧文字机械拼接。

完成迁移后，“三维”不再是钧钧或小雪需要独立维护、独立展示的第二份队伍描述；它只是队伍画像内前三项的历史兼容投影。队伍画像是唯一判断正源，Web、Wiki、专项 Skill 和单场资料均从它读取或展示。

### 11.3 日常积累与阶段维护

TK、战报、外部搜索、赛后观察和钧钧的交易记录都是材料，不是第二份画像。它们保留原文、来源、时间、对象和身份；钧钧的交易判断不得改写成客观事实。

钧钧自然提出“维护 BLG”“更新 LPL 队伍情况”或“把这一阶段队伍重新整理一下”时，小雪应：读取该队现有画像、当前首发和 TS；按范围读取近期相关 TK、钧钧记录及需要的战报；只把足以改变五项画像的结论写入候选；区分已证实、相互冲突和证据不足；完成写入后读回唯一队伍画像。她不再要求钧钧分别确认三维和画像，也不因单条 TK 自动改写长期结论。

首次全量维护的范围是当前 LPL / LCK 队伍。小雪逐队完成同一套五项画像，资料不足则明确写“资料不足，暂不下结论”，不编造、不用国际赛遗留资料补齐、不把过时阵容写成当前事实。

### 11.4 TS、首发与画像的关系

TS、sigma、样本数、当前首发、赛果和版本是随时间变化的事实或信号，保留在各自正式数据源中。它们用于维护时检验和修正画像，但不替代五项文字，也不被写成队伍永久性格。读取队伍时可与画像一同展示；画像正文只在这些事实确实改变队伍打法、核心链、输赢方式或 BP 倾向时更新。
